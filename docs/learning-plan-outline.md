# テストエンジニア育成講座 学習プラン（v0.2）

## 対象と目的

- **対象**: QA組織テストチームの中途入社メンバー（テスト実務未経験）
- **ゴール**: 「言われたテストを実行する人」から、**仕様把握 → テスト分析・設計 → 実行管理 → 品質報告を一人で回せる人材**へ
- **対象ドメイン**: 業務システム（例題は経費精算システムで統一）
- **方針**:
  - 考え方・マインドセット重視。細かい技法は「道具の存在と使い所」を教え、深掘りは書籍へ誘導
  - ISTQB Foundation (CTFL 2023 V4.0) の体系をベースにしつつ、現場で使う順番に再構成
  - JSTQB受験は意識するが前面には出さない（各回末尾にシラバス対応章を小さく記載する程度）
  - 毎回ワークを入れる

## 全体構成: 全3回（各90分）

| 回 | テーマ | 対応HTML |
|---|---|---|
| 第1回 | テストとは何か — マインドセットと基礎 | `slides/phase1.html` |
| 第2回 | 仕様を読み、テストを設計する | `slides/phase2.html` |
| 第3回 | テストを管理し、品質を語る | `slides/phase3.html` |

### 第1回 テストとは何か — マインドセットと基礎（90分）

| 時間 | 内容 |
|---|---|
| 5分 | オープニング: この講座のゴール |
| 18分 | なぜテストをするのか — 品質情報を届ける仕事。業務システムの不具合コスト実例。**エラー→欠陥→故障の因果連鎖**（用語の土台）＋その連鎖のどこに手を入れるかで**QC／QA**に分かれることに軽く触れる（対比は図で見せるだけ。深掘りはStep2第5回）。※テストはQCの主要な活動であって「動かすこと」に限らない — **動的テスト（故障→欠陥）と静的テスト（欠陥を直接発見）**の区別をここで立てておく |
| 15分 | **ワーク①**（個人5分→全体共有10分）: 「その"バグ"は、どこにあったのか」→ **経費データ連携の金額ズレ**（経費精算システムはCSVに税込で出力、会計システムは税抜として受け取り消費税を上乗せ。IF仕様書は税抜と明記。連携テストは「取り込みがエラーにならない」確認のみ。テスト中に合計金額の違和感がありながら記録されず流れた）を**故障→欠陥→エラーの3つに分解**（根本原因はQAの領域なので扱わない）。前セクションの因果連鎖を実地で使う。解答例は税の思い込みだけで終わらせず、**つないだ状態での検証不足・異常の兆候を扱っていないこと・組織間コミュニケーション不足**まで引き出す。「観測した事実（故障）と原因の推測」の書き分け＝第5セクション「良い不具合報告」への布石にもする。※エラーは**欠陥を作り込んだ開発・テスト側の判断に絞る**（締めで気づいた経理は利用者であり、故障の発見者。エラーには挙げない）。旧題材のMars Climate Orbiterは、前提知識の負荷が高くNASAのroot causeとISTQBの欠陥が用語衝突するため2026-07-31に差し替え |
| 8分 | テストの7原則（業務システムの実例つき）※原則1は前セクションで説明済み。厚く話すのは原則2・3・4に絞り、5〜7は表を指す程度 |
| 12分 | テストの全体地図: テストプロセス、レベル/タイプ、Vモデルとシフトレフト、アジャイルテストの4象限 ※時間をかけるのはテストプロセス図とVモデルの2枚。4象限は2軸の意味のみ紹介し、詳細は各自参照。**Q3をQAの縄張りとして教えない**（抜けをチーム全体でカバーするためのモデル。Q2の受け入れ条件づくり・Q4の非機能にも関わる） |
| 17分 | 良い不具合報告 — 不具合チケットは開発者への報告文書。**「事実と推測」＝「故障と欠陥」**の対応づけ（用語の実践編）。Severity/Priority |
| 10分 | **ワーク②**: テスト中の**走り書きメモ**（100円で弾かれる／99円は通る／仕様3.2は「以下」だった"気がする"／消費税のバグでは？という推測／Sさんの伝聞／並び順という別事象／「環境はいつものやつ」）から不具合チケットを起こす。ダメチケットは導入で見せるだけ。狙いは**①事実 ②推測・伝聞 ③別の事象 ④確認が必要 の4区分に仕分けること**で、清書は仕分けの結果にすぎない。難易度調整: スライドにヒントは載せない。手が止まったペアにだけ口頭で「『たぶん』『気がする』が付く文は事実ではない」と出す（講師用ノートに記載）。時間が押したら仕分けだけで切り上げ、清書は宿題 |
| 5分 | まとめ |

### 第2回 仕様を読み、テストを設計する（90分）

主旋律（この回で唯一残したいもの）: **仕様を鵜呑みにせず、テスト観点とテスト条件を整理し、根拠のあるケースへ落とす。**

| 時間 | 内容 |
|---|---|
| 3分 | 今日の道すじ — 「仕様を読んで疑問を出す → 観点 → 条件 → ケース」の一本道を図で先に見せ、**これがテスト分析（何をテストするか）とテスト設計（どうテストするか）という活動そのもの**だと名前を与える |
| 15分 | 仕様把握の勘所: テストベースの広さ、**書かれていないこと（3層の氷山）**、仕様の穴の嗅ぎ分け、質問力、ドメイン知識とユーザー目線。ドメイン知識の「身につけ方」はdetailsへ |
| 15分 | **ワーク①**: 曖昧な経費申請仕様から「開発者への質問リスト」を作る（質問5つ＋**A/B/Cの優先度付け**。数ではなく判断を問う） |
| 10分 | 観点 → 条件 → ケース（**「金額と承認ルート」1題材で3段階を貫く表**）、7つの引き出し、リスクベースの濃淡。SFDIPOT/RCRCRCの由来はdetailsへ |
| 10分 | **ワーク②**: 経費申請機能の観点ブレスト（**12個程度**。トップ1について「なぜ／何が起きて困る／根拠」を説明） |
| 15分 | 技法ダイジェスト: **仕様ベースの技法（同値分割・境界値／デシジョンテーブル／状態遷移）と経験ベース（探索的テスト）を役割で分けて**紹介 + 良いテストケースの条件 |
| 12分 | **ワーク③**: 境界値+デシジョンテーブルでケース化（**条件を固定して提示**: 金額2値×役職3値、判断できないマスは「要確認」） |
| 5分 | まとめ・出口問題（技法練習は課題図書へ） |
| 5分 | 調整余白（指示確認・グループ編成・質疑応答） |

### 第3回 テストを管理し、品質を語る（90分）

| 時間 | 内容 |
|---|---|
| 5分 | 前回の振り返り |
| 20分 | テスト計画と見積り: スコープ、開始/終了基準、業務システム特有の重み（環境・テストデータ・移行） |
| 20分 | 進捗と品質を読む: 消化曲線とPB曲線の見方、「グラフは嘘をつく」パターン集 |
| 20分 | **ワーク①**: PB図4パターン+状況カードで「リリース可否」をチーム判断 |
| 10分 | バグトリアージの実践: 重要度×頻度×回避策、テスターは意思を持って材料を出す |
| 10分 | テストの終わり方: 残存リスクを語れることがゴール、サマリーレポート |
| 5分 | まとめ・これからの学び方（キャリアパス・JSTQB FL・課題図書・コミュニティ） |

## 運用案

- ペース: 週1回 or 隔週、全3回で約1ヶ月
- 宿題は課さない（メンバーの時間的余裕を考慮）。課題図書は任意の推奨にとどめる
- 課題図書（案）: 『ソフトウェアテスト講義ノオト』『ソフトウェアテスト技法練習帳』、JSTQB FLシラバス2023 V4.0（無料PDF）
- 効果測定: 第3回後に小さな卒業課題（仕様→観点→ケース抜粋→サマリーレポート1枚の通し演習）をOJT側で実施

## 決定事項の記録

- 2026-07-31: **第2回をレビュー指摘に基づき再構成**（詰め込みすぎで中心概念がぼやける、との指摘）。主旋律を「仕様を鵜呑みにせず、テスト観点とテスト条件を整理し、根拠のあるケースへ落とす」の一本に絞り、以下を実施:
  - **「暗黙の仕様」という言い方をやめた**。テスターが常識で仕様を決めてよいと誤解されるため。氷山図を「明文化された仕様／明文化されていない期待・業務ルール／まだ合意されていない仮説・疑問」の3層に分割し、**推測を仕様に格上げできるのは確認・合意・記録だけ**であることを明示
  - **観点 → 条件 → ケースを「金額と承認ルート」1題材で貫く表**を追加（この回の最重要概念なのに境界が曖昧だったため）。7つの引き出しの右列も観点の粒度に統一（従来はテスト条件寄りの記述が混在）。「観点の抜けはケースを増やしても埋まらない」→「**同じ観点の中だけでケースを増やしても、別の観点の抜けは埋まらない**」に修正
  - **「代表的な技法4つ」という数え方を撤回**。数えると5つあり、かつ探索的テストは経験ベースで役割が違うため、**仕様ベース（条件→ケースの変換）／経験ベース（条件そのものの発見）**の2分類で提示
  - 境界値分析に**2値・3値は扱わない旨の宣言**を追加。「同値クラスから1点でよい」→「1点が基本形。内部処理が異なる疑い・高リスクなら足す」
  - デシジョンテーブルの「埋まらないマスは仕様の穴」→**仕様未定義／成立しない組み合わせ／結果に影響しない条件の3分類**に修正（全部を仕様漏れ扱いすると質問リストが膨れ、本当に必要な質問が埋もれる）
  - 探索的テストの「自由に触る」を**目的・時間箱・記録・振り返りの4点セット**に置換。「まず30分探索」は条件付きの表現に緩和（Step2第4回の記述も追随修正）
  - 時間配分を実測ベースに（導入3分と調整余白5分を明示、セクション1は20→15分、ワーク③は10→12分）。ワーク③は条件を固定して提示
  - 表現の断定を弱める修正（「ここの確認だけなら誰でもできる」「ゼロから観点をひねり出すのは無理」「マニュアルと実装の食い違いはそれ自体が不具合」「現行が最大のテストベース」「口頭で得た仕様は文書化した瞬間に資産」等）
  - シラバス対応を CTFL v4.0.1 の正しい節番号に修正（4.1は技法の概要、ブラックボックスは4.2。リスクによる濃淡は5.2.3）
  - 見送り: 「ユーザーストーリー・業務シナリオからのテスト設計」の追加。枠を作るには探索やヒューリスティックの詳細をさらに削る必要があり、今回は主旋律の明確化を優先した
- 全3回構成（各フェーズ1回・90分）— 2026-07-07決定
- 第1回セクション1に「エラー・欠陥・故障・根本原因」の因果連鎖を追加（15→20分、7原則を15→10分に圧縮して90分維持）— 2026-07-30決定
- 第1回では「根本原因にアプローチするのがQA、欠陥・故障にアプローチするのがテスト＝QC」を図の対比で軽く示すだけに留める（新人には再発防止・プロセス改善は早いため、活動の呼び分けの地図だけ渡す）。QC/QAの本格的な対比表はStep2第5回 — 2026-07-30決定
- 用語の使い分けの実践（報告に書くのは故障、欠陥は推測／欠陥は成果物の属性で人の属性ではない）はセクション1では扱わず、**セクション5「良い不具合報告」に置く** — 2026-07-30決定。セクション1は用語の定義だけに絞り、実践は必要になった場所で出す。これに伴いセクション1を20→18分、セクション5を15→17分
