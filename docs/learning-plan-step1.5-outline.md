# テストエンジニア育成講座 Step1.5（管理編） 学習プラン（v0.1）

## 対象と目的

- **対象**: Step1（基礎編・全3回）を修了し、テスト管理やチケットの取り回しを任され始めたメンバー
- **背景（2026-10に明示された現場課題）**: テスト管理を任せた後輩が、チケットを取り回せない。テスターから上がったチケットを精査できず、開発とのコメントのやり取りや解決までの道筋が描けない。結果として「そのまま横に流す」か「開発に渡すべき原因調査を自分で抱え込む」かのどちらかになる
- **ゴール**: 「テストを主担当として回せる」から、**チケットを止めずに、起票からクローズまで運べる人材**へ
- **対象ドメイン**: Step1・Step2と同じく業務システム（例題は経費精算システムで統一）
- **方針**:
  - JSTQB Advanced Level テストマネジメント Version 3.0（V3.0.J02、ISTQB CTAL-TM v3.0）の **2.3 欠陥マネジメント**を背骨にし、隣接する 2.1 テストメトリクス／1.1.2 モニタリングとコントロール／1.2.1 ステークホルダー／1.5.4 ふりかえり を合わせて扱う
  - シラバスが定めるのは枠組み（状態・所有者・レポート情報・機能横断の判断）まで。日々の判断の型（5つの問い、依頼コメントの4点など）は**本講座の実務補足**として足し、各回末尾でシラバス由来の内容と分けて明記する
  - 「経験するしかない」領域を、**予測 → 答え合わせ**の形で構造化する（第2回のチケット追体験ワーク）
  - 中心メッセージは3回共通で一つ: **管理担当の仕事は、問題を自分で解くことではなく、解決に必要な人と情報を揃えて、判断を前へ進めること**
  - 毎回ワークを入れる

## 位置づけ

- Step1 第1回「良い不具合報告」（書く側）、第3回「バグトリアージ」（材料を出す側）の続き。今度は**受け取る側・動かす側**
- Step2（戦略・上流・AI）とは独立。Step2より先に受けても後に受けてもよい。第3回の「欠陥が集中する機能」「上流で作り込まれる欠陥」がStep2 第4回・第5回への橋になる
- 回の番号はStep2（第4〜6回）と衝突しないよう、**「管理編 第1〜3回」**とする（ファイル名は `phaseM1`〜`phaseM3`）

### 管理編 第1回 チケットを受け取る（90分）

| 時間 | 内容 |
|---|---|
| 7分 | チケットはなぜ止まるのか — **横流し**と**抱え込み**。正反対に見えて、どちらも「次の一手は何か」という問いが抜けている。3つの型の図（横流し／抱え込み／進める）。管理担当の仕事の定義 |
| 18分 | 欠陥マネジメントの地図: **不正（anomaly）**として受け取る（正体は6種類: 製品の欠陥／テスト側の誤り／仕様の未定義／環境／重複／要望）。**欠陥ワークフロー**（オープン／進行中／却下／解決／クローズ＋拡張の明確化・再オープン・見送り）と**「状態＝今だれの番か」**。チケットに載っていてほしい情報（シラバス 2.3.5）。Azure Boards への読み替えはdetails |
| 20分 | **5つの問い**（何が起きている／情報は足りている／何として扱う／次に誰が何をする／次の状態になる条件は）と**一次判断フロー（SVG）**。問4の地図（その問いに答えられるのは誰か）。**「調べる」と「渡す」の線引き**（一次切り分けは時間を区切る。例15分。「渡してから調べる」）。戻すときの型 |
| 25分 | **ワーク①**（個人8分→グループ10分→共有7分）: 今朝届いた6件を一次判断する。6件は意図的に行き先が全部違う — 情報不足で戻す／急ぎの欠陥候補／仕様の確認／間欠で抱え込みたくなる欠陥候補（重要度の見直し）／重複に見えて新情報あり／仕様どおりだが要望。追加1件（環境起因）は時間が余ったグループ用 |
| 12分 | 講評: 一次判断でよくある7つの失敗。**起票者が付けた重要度を見直す**（重要度と優先度を分けて語る） |
| 5分 | まとめ |
| 3分 | 調整余白 |

### 管理編 第2回 チケットを運ぶ（90分）

| 時間 | 内容 |
|---|---|
| 5分 | 前回の振り返り |
| 12分 | 欠陥の扱いは一人では決めない: **機能横断的な欠陥マネジメント**（欠陥マネジメント委員会、利点・リスク・コスト、トリアージ）。誰が何を判断し、テスト側は何を材料として出すか。トリアージに持ち込む前に揃えるもの。**ツールは会話の代わりにならない**（2往復したら話す、話したら書き戻す）。アジャイル／ハイブリッドはdetails |
| 18分 | 伝わるコメントの型: **依頼コメントの4点**（分かっていること／お願い／いつまでに・なぜ／返してほしいもの）。**返ってきた言葉別・次の一手**（再現しません／仕様です／直しました／次回にしたい／調査中です／返事がない）。言い方の作法。**ミニワーク**（5分）: 「どうなってますか？困っています」を4点で書き直す |
| 25分 | **ワーク②**（グループ18分→ふりかえり7分）: **チケット追体験**。1件の履歴を6場面に区切り、続きを開く前に「次の一手」を予測する。題材は「兼務者の5万円超の申請が課長承認だけで承認済みになる」。横流し→再現しません→条件を絞る→仕様どおりで却下→仕様担当へ→見送り提案→臨時トリアージ→修正→確認テストで別事象→クローズ。最後に**ボールの軌跡（スイムレーン図）**でふりかえる |
| 12分 | 止まったチケットを動かす: 5つの止まり方（最後は「自分が持っている」）。**滞留の目安**を先に決める。**フォローの3段階**（チケット→直接→エスカレーション）。エスカレーションは告げ口ではない（主語は人ではなくチケット） |
| 10分 | 終わらせ方: 「直しました」で聞く3点、確認の3層。クローズ／再オープン／新規起票の使い分け。却下・再現不可・見送りで残すもの（見送りはテスト完了報告の残存リスクへ） |
| 5分 | まとめ |
| 3分 | 調整余白 |

## OJTとの連携（任せる側向け）

講義だけでは定着しない領域なので、OJT側の動きとセットにする。詳細は第3回セクション7のdetailsにも記載。

- **学び方の配分の目安**: 座学2割／過去チケットの追体験4割／実案件＋レビュー4割
- **過去チケットの追体験**（第2回ワーク②と同じ形式）: クローズ済みチケットのうち、往復が3回以上・却下や見送りで終了・再オープンあり、のものを選ぶ。起票内容だけ見せて「次の一手は？」→コメントを1つずつ開示→最後に「なぜこの結論になったか」を説明させる。1件10〜15分、週2〜3件、合計20〜30件が目安。個人名は役割名に置き換える
- **任せ方の4フェーズ**: ①見せる（判断の理由を声に出す）→②判断だけ任せる（提案をレビュー）→③低リスクを任せる→④例外だけ相談。「全部任せる／全部見る」の二択にしない
- **評価**: 6観点（情報不足の検出／分類／重要度・優先度／次の持ち主／コメント／クローズまでの追跡）×10件＝60点で月次に付ける。合計より「どの観点が低いか」を見る。人事評価には流用しない
- **チームで決めておくとよいもの**（講義中「例」として出しているもの）: 一次切り分けの時間制限、滞留の目安、相談してから動くチケットの基準、再オープンか新規起票かのルール

## 決定事項の記録

- 2026-10-07: Step1.5を新設。全3回・各90分。テーマは欠陥マネジメント（チケットの取り回し）に絞り、3回とも同じ背骨で「1件 → 1件の一生 → 全体」と距離を広げる構成にした。Advanced Test Management の他テーマ（見積り、戦略、ツール、チーム）を1回ずつ並べる案は採らなかった — 現場課題がチケットの取り回しに集中しており、3回かけて判断の型を反復させるほうが効くと判断したため
- 2026-10-07: 第3回にだけ隣接テーマ（メトリクス、報告、ふりかえり）を入れた。「1件ずつは正しく動かせるが全体が見えていない」が次に来る壁であり、欠陥情報の使い道（2.3.5／2.3.6）を扱うなら 2.1 と一緒に扱うのが自然なため
- 2026-10-07: 「管理担当は原因調査をしない」とは教えない。**一次切り分け（テスト側の仕事）と原因調査（開発の仕事）を分け、一次切り分けは時間を区切る**、と教える。禁止しているのは調べることではなく、黙って持ち続けること。Step2 第6回の「インプロセスQA（開発との協働）」と矛盾させないため
- 2026-10-07: 判断のフローチャートは、一次判断（第1回）だけを1枚のSVGにした。渡したあとの分岐（返答別の対応、フォロー、クローズ）はフローにすると巨大になるため、表（返ってきた言葉別・次の一手）と3段階の図に分けた
