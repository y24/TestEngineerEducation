テストエンジニア育成講座 — 第3回（90分）

テストを管理し、品質を語る

テスト計画と見積り、PB曲線の読み方、バグトリアージ、そしてテストの終わり方。「回す」力を作る。

今日のゴール

  • テスト計画に何を決めて書くべきかが分かる（特にテスト目的・開始基準・終了基準・やらないこと）
  • P曲線とB曲線（PB曲線）を読み、グラフの裏にある現場の状況を確かめてから判断できる
  • 読んだ結果を打ち手（テストコントロール）につなげられる
  • バグトリアージで、テスターとして意思を持った材料を出せる
  • 「テストの終わり」を残存リスクの言葉で語れる

1. テスト計画と見積り — 始める前に勝負は半分決まる 20分

テスト計画に書くこと

テスト計画書は儀式の文書ではなく、関係者と交わす「合意」のかたまりです。最低限これを決めます。

項目決めること・ポイント
テスト目的このテストで何を確認し、どの判断を支援するのか。例:「主要業務がリリース可能な状態かを判断する」「変更による既存機能への影響を評価する」。ここが決まっていないと、アプローチも終了基準も根拠が弱くなる
スコープテストする機能・レベル・タイプ。そして「やらないこと」を明記する（第2回参照）。やらないことが書かれていない計画は、後で「やってくれてると思った」を生む
アプローチどの領域をどの濃さで（リスクベースの濃淡）。新規機能は設計ベースで厚く、既存部はリグレッション中心、など
開始基準（エントリ）テストを受け入れる条件: 対象ビルドについて合意した前段のテストが完了している（単体テスト、開発者テストなど）、主要動線のスモークが通過している、環境・テストデータが揃っている、など
終了基準（イグジット）「いつ終わってよいか」: ケース消化率、未解決バグの重要度別件数、カバレッジ、残存リスクを説明できる状態か、など。始める前に決めておくのが肝
スケジュール・体制誰が・いつ・何を。バグ修正待ちと再テストの時間を織り込む
リスクと前提「環境提供が遅れたら開始も遅れる」等、崩れたら計画が変わる前提を書いておく — これが後の交渉材料になる
モニタリング・報告何を測り、誰に、どの頻度で報告するか。遅延や品質リスクが起きたときのエスカレーション先も決めておく
成果物テストケース、実行結果、欠陥レポート、テスト完了レポートなど、何を残すか

開始基準を軽視すると地獄が始まる

経験の浅いチームが最も痛い目に遭うのがここです。単体テストが不十分なままシステムテストを始めると、 初日から基本動作のバグで手が止まり、本来の観点のテストに一切進めないという消耗戦になります。

マインドセット 基準を満たさない成果物は、原則として受け入れを保留する。 ただし、現実には期限や体制の都合でそのまま待てないこともある。その場合は 対象範囲を限定する／未通過部分を除いて開始する／追加リスクを明示するなど、 開始条件を再合意してから進める。いちばん危険なのは、条件を満たしていないことを黙って引き取ること。

見積りの現実 — 実行時間だけ数えると足りなくなる

  • テスト見積り ＝ 実行時間だけではない。分析・設計・データ準備・環境確認・チケット起票・再テスト・リグレッションを含める
  • 経験則: バグ対応（起票・確認・再テスト）で実行工数と同等以上かかることも珍しくない。バグが多い前提の機能なら、なおさら
  • 業務システム特有の重さ: テストデータ作り（マスタ・権限・月次状態の組み合わせ）と環境・連携先の調整は、見積りから最も抜けやすく、最も遅延を生む
  • 締め日・月次処理があるシステムは「その日付にならないと確認できない」テストがある。カレンダーを最初に確認する

ではどのように見積もるのか — 最初の一歩

  1. テスト活動を小さな作業に分解する（機能単位・活動単位）
  2. 各作業を過去実績または類似作業から見積もる
  3. 不具合対応・再テストの予備工数を加える
  4. 環境・仕様未確定・外部連携などリスクの幅を加える
  5. ひとつの数字ではなく、前提つきの「範囲」で提示する
見積りの出し方（例） 基本見積り: 8人日 ／ 不具合対応の予備: 2〜4人日 ／ 環境リスク: 1〜2人日
合計: 11〜14人日
前提: テスト環境が予定日に提供され、主要スモークが通過していること。前提が崩れた場合は再見積り。
※ 一点で答えず幅と前提で答えるのは、逃げではなく不確実性の可視化。ここが崩れたら計画が変わる、という交渉材料にもなる。
マインドセット 計画は「約束」ではなく「その時点の情報で合意した仮説」。状況が変わったら隠さず更新して再合意する。 黙って頑張って最後に「間に合いません」が最悪のパターン。

2. 進捗と品質を読む — P曲線とB曲線 15分

PB曲線 — 2本を同じ時間軸で重ねて読む

  • P曲線: テストケースの実行・消化の累積推移（予定と実績）。テストがどれだけ進んだかを見る
  • B曲線: 検出した欠陥数の累積推移。欠陥の検出ペースがどう変化しているかを見る
  • PB曲線: この2本を同じ時間軸で組み合わせて読むもの。テストの進み方と欠陥の検出傾向はセットでしか意味を持たない
  • B曲線だけを見ても、テストが進んでいないのか品質が良いのかは区別できない

B曲線の基本の見方

典型例のひとつに、序盤は検出が少なく、中盤に増え、終盤に水平へ近づくS字形があります （「曲線が寝る」＝検出ペースの低下）。 ただし、リスクの高いケースから先に実行すれば序盤から急増して後半に寝るし、機能単位で順に流せば階段状にもなる。 形は実行順序やテストの進め方で変わるので、S字であること自体を品質の証拠にはしません。

グラフだけでは理由を語れない — 4つのパターン

形ありがちな解釈本当に確かめるべきこと
A 順調に収束。リリース可能 P曲線も計画通りか。難しいケースを後回しにして寝ているだけではないか。終盤の消化ケースの中身を見る
B 品質が悪い。リリース不可 本当に品質問題か、それともテストが優秀でバグを掘り当て続けているのか。バグの重要度の内訳と発生機能の偏りを見る。特定機能に集中しているなら、その機能の作り直し判断も視野に
C 早く収束した。品質が良い 一番危険な形。テストが止まっていないか（環境障害・ブロックバグ・要員離脱）、簡単なケースだけ消化していないか、バグ起票が滞っていないか。P曲線とセットで見ることで、疑うべき原因を絞り込める（絞り込んだ後、現場に確認して初めて原因が分かる）
D よく分からない動き ケース消化をまとめてやっていないか（週末にまとめて実行）、バグ報告が遅延・まとめ起票されていないか。運用の問題であってプロダクト品質の問題ではないかも

読む前に確認する — その数字は「何を」「いつ」数えたのか

グラフを読む前に、まず数え方の定義を確認します。ここが揃っていない数字は、いくら丁寧に読んでも意味を取り違えます。

確認することありがちな食い違い
「消化」の分子は何かPass だけか、Fail も含むか。Blocked は？ 実行したが証跡未登録は？ — 同じ「消化率85%」でも中身がまるで違う。Pass/Fail/Blocked/未実行の件数を並べて出すほうが、率よりずっと判断しやすい
欠陥はどの日付で数えたか検出日・起票日・確認日・修正日・クローズ日のどれか。起票日で描けば、まとめ起票の運用は階段状になる。検出日で描けば別の形になる
母数は何か全ケースか、対象リリース分か、対象機能のみか。分母が動くと率だけが動く
現場の鉄則 メトリクスは会話の入口であって、結論ではない。グラフを見ただけで「リリースできる/できない」ではなく、 その形になっている理由を実際に確認して「グラフ＋その裏で起きていること」を必ずセットで語る。
業務システムの現場から 消化率95%・バグ曲線も寝ていて「順調」に見えたプロジェクト。残り5%が「月次締めバッチ」のケースで、 実行できる日が月末しかなく、最後の最後で重大バグが噴出——という失敗は本当によくある。 残ケースの「数」ではなく「中身」を見る癖をつける。

3. ワーク① このプロジェクト、リリースしてよい？ 20分

ワーク（グループ15分 → 発表5分）

グループごとに、上のA〜Dいずれかのグラフを担当し、対応する下の状況カードを読み込みます。

リリース判定会議に向けて、次の5点を3分で説明できる形にまとめてください。

  1. 現時点の品質状況（何が言えて、何がまだ言えないか）
  2. リリース時点の見通し（残り5営業日で何がどこまで終わるか）
  3. 推奨: Go ／ 条件付きGo ／ No-Go ／ 判断保留 の4択から選ぶ
  4. その条件と根拠（「何が満たされればGoか」を具体的に）
  5. 追加で確認すべき情報（今は分からないが、判断に必要なこと）

発表後、他グループは「その判断、数字の裏は取れてる？」の視点でツッコミを入れます。

※ 無理に二択のGo／No-Goを出す必要はありません。テスト担当者の実力が出るのは、 「何が分かれば判断できるか」を示せることです。

プロジェクト共通設定（全カード共通） 経費精算システム刷新プロジェクトのシステムテスト。テスト期間は20営業日で、本日は15日目。 テストケースは全500件。リリース判定会議は5営業日後。 終了基準は「消化率100%、未解決の重要度高チケット0件」で計画時に合意済み。
数え方の定義: このワークでは、結果がPassまたはFailまで確定したケースを「消化済み」とする。 Blocked・未実行・結果未登録は未消化として扱う。 なお、Fail件数と欠陥チケット件数は一致しない（1つの欠陥が複数ケースに影響することがある）。

4. 講評 — 読んだ後にどう動くか（テストコントロール） 10分

モニタリングの次は、コントロール

状況を読むのがモニタリング、読んだ結果に応じて計画・優先順位・スケジュール・体制を調整するのがコントロールです。 テスト管理は「観測して報告する」で終わりません。読んだ後にどう動くかまでがセット。

観測した状況確認することコントロールの例
消化が遅れている環境、要員、ケース難度、バグ待ち優先順位変更、範囲調整、要員追加、日程再計画
高重要度バグが集中共通原因、機能の構造的な問題該当機能を一時停止、集中修正、再設計の検討、リリース分離
B曲線が早く寝たテスト停止、簡単なケースへの偏り高リスクケースの前倒し、環境復旧、追加テスト
再テスト待ちが増加修正速度、ビルド頻度修正確認枠の確保、ビルド頻度の見直し

5. バグトリアージ — 直す順番を決める会議の回し方 10分

トリアージとは

見つかった欠陥を、すべて同じリリースで修正できるとは限りません。 限られた時間の中で、どれをいつ直し、どのリスクを受け入れるかを関係者で合意するのがトリアージです。

トリアージで合意するのは修正優先度だけではありません。 そもそも欠陥かどうかの分類（仕様どおりではないか）、重複チケットではないか、変更要求として扱うべきか、重要度、修正優先度、対応するリリース、担当者、修正しない場合の理由と承認者まで含みます。

判断軸問いかけ
業務影響（重要度）発生すると業務が止まるか？ お金・法令に関わるか？ 影響するユーザー数は？
発生頻度・条件誰でも毎回踏むのか、特定条件のみか。
回避策の有無運用でしのげるか（手作業で代替できるか）。回避策があれば優先度を下げられることがある。下げてよいかは、その回避策が確実に機能するか／全ユーザーが実施できるか／手順ミスが起きないか／運用コストが許容できるか／法令・契約・監査上許容されるかで決まる
修正リスク直すことで他を壊さないか。リリース直前の修正は、それ自体がリスク
回避策があっても下げられない例 「回避策あり: 毎月、経理担当者20人がExcelで手修正する」——回避策は存在しているが、 20人×毎月の作業と、手修正による二次的な誤りのリスクを負うことになる。 回避策の有無ではなく中身と運用コストで判断する。

テスト担当者の役割 — 意思を持って材料を出す

  • 優先度の最終決定はプロダクト側の仕事。しかし「決められる材料」を揃えるのはテスト担当者の仕事: 再現条件、影響範囲、頻度、回避策の有無まで調べて出す
  • 単なる報告係にならない。推奨＋根拠まで言う。このとき重要度（業務影響の大きさ）と修正優先度（いつ直すか）を分けて語ると伝わる（第1回で扱った区別）:
    「この欠陥は、締め日に経理担当者全員の業務を停止させるため、重要度Highと考えます。締め日前に回避策を用意できないため、修正優先度P1を推奨します」
  • 「直さない」と決まったバグは、既知の問題として残存リスクに記録する。ここでうやむやにすると、リリース後に「聞いてない」が起きる
マインドセット トリアージは開発 vs テストの勝負の場ではなく、限られた時間をどこに使うかをチームで決める場。 「全部直してください」は思考停止。優先順位を語れるテスト担当者がチームの信頼を得る。

6. テストの終わり方 — 残存リスクを語る 10分

テストは「残テストケースが0になったら終わり」ではない

現場でいちばん陥りやすいのが、ケース消化率100%＝テスト完了という感覚です。 進捗表の残数が0になると「終わった」と言いたくなりますが、それが意味するのは 「計画したケースを予定どおり実行した」ことだけで、 「品質が出荷できる状態にある」こととは別の話です。 （同じく「バグが0になったら終わり」も成立しません。検出済み欠陥が0件になることはあっても、未検出の欠陥まで含めて「欠陥が存在しない」ことは証明できない——第1回・7原則）。

状況判断
残ケース0。でも重大バグが未修正／再テスト待ち 終われない。消化は終わってもリスクは残っている
残ケース0。でも実行中に「このケースでは足りない」と分かった領域がある 終われない。ケースを追加するか、テストが薄い領域として明示して残す
不具合によりNG／Blockのケースが残っている。重要度と期限とのトレードオフで修正なしで合意済み 残数だけでは決まらない。そのバグの重要度・業務影響・回避策の有無で判断する。軽微＋回避策ありなら「既知の問題」として残したまま終える判断もありうる（決めるのはリリース判断者、材料を出すのがテスト担当者）
期限が来たので残ケースを実行せず打ち切り 計画したテスト範囲は未完了。ただし、ステークホルダーが追加テストを行わずに本稼働するリスクを確認し、受容したうえであれば、テスト活動としては正式に終了・クローズできる。未実行範囲とその影響を完了レポートに明記するところまでがセット
混ぜてはいけない3つ ①計画したテスト範囲が終わったか ②テスト活動を終了してよいか ③リリースしてよいか — この3つは別の判断です。
終了基準はテスト活動を終了できるかの基準であって、リリース基準と完全に同じとは限りません。 テスト担当者は終了基準の達成状況と残存リスクを報告し、最終的なリリース判断はリリース判断権限を持つ人が行います。

つまり、残ケースが0でも終われないことがあり、残っていても終われることがある。 テストの終わりは、消化数でもバグ数でもなく計画時に合意した終了基準を満たしたかどうかで判断します。 終了基準は「消化率100%」だけではなく、重要度の高いバグが残っていないか・重要機能をカバーできたか・残存リスクを説明できるかまで含めて計画時に決めておくもの。 満たせない場合は何が残っているかを明らかにして、リリース判断者に委ねるのが正しい終わり方です。

テスト完了報告 — 最後の成果物

書くことポイント
実施したこと／しなかったこと計画とスコープに対する実績。やらなかったことを隠さない
結果サマリー消化数（ステータス別）、欠陥数と重要度内訳、検出傾向（グラフ＋裏の状況説明）
計画との差異予定期間・工数・スコープ・アプローチから何が変わったか。阻害要因は何だったか
残存リスク未解決欠陥（回避策つき）、テストできなかった領域とその理由、薄くした領域
判断に影響する不確実性実行結果の信頼性、本番との環境差異、十分な証拠がない領域
推奨と条件リリース推奨／条件付き推奨／延期推奨と、その根拠
学んだこと・改善事項次回の計画・環境・設計・運用に反映する事項

これが第1回の冒頭に言った「テストの成果物は品質に関する判断材料」の最終形です。 良い完了報告が書けること＝テストを主担当として回せること、と言ってもいいくらいです。

まとめ・これからの学び方 5分

3回の講座の全体像

  • 第1回: テストは品質情報で意思決定を支える仕事。テストの限界を知り、チケットという武器を持った
  • 第2回: 仕様を疑って読み、観点→条件→ケースの順で、根拠を説明できるテスト設計をする
  • 第3回: 計画で合意し、P曲線・B曲線の裏を読んで打ち手につなげ、トリアージで意思を出し、残存リスクを明らかにしてテストを終える

この3つのループを、小さな案件でよいので関係者と合意を取りながら、主担当として一連の活動を回せるようになるのが次のステップです（一人で抱え込むこととは違います）。

この先のキャリア — テストの先に広がる道

「テスト設計・管理を主担当として回せる」はゴールではなく、キャリアの分岐点です。 上下関係ではなく分岐で、どの道に進んでも、この3回で扱った「考え方」がそのまま土台になります。 （詳しい説明は下のリンクと持ち帰り資料に置いておきます。ここでは図だけ見てください）

持ち帰り: それぞれの道の中身（講義では読み上げません）
  • テストスペシャリスト / テストアーキテクト: テスト分析・設計そのものを極める道。大規模なテスト設計を構造化し、チームの設計標準を作る。第2回の内容を深めていく方向（ISTQB Advanced Level: Test Analyst が指針になる）
  • QAエンジニア / 品質保証: テスト工程の外に出て、品質データの分析、開発プロセスの改善、上流での欠陥予防に関わる道。「テストで品質を測る」から「プロセスで品質を作り込む」へ視点が一段上がる。バグをどう検出するかではなく「そもそもなぜこのバグが混入したか」を追うのが入口
  • SET / テスト自動化エンジニア: コードを書いてテストを支える道。リグレッションテストの自動化、CI/CDへの組み込み、開発者へのテスタビリティ（テストしやすさ）の提案。開発スキル×テストスキルの掛け算で希少価値が高い
  • テストマネージャー / QAマネージャー: チーム全体の計画、体制づくり、テスト戦略／品質戦略の立案。第3回で扱った「回す力」を組織スケールに広げる道
