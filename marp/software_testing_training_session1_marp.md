未経験者向け ソフトウェアテスト基礎講座

# 今日の位置づけ

この講義では、ソフトウェアテストを単なる確認作業ではなく、

**品質に関する判断材料を集める専門的な活動**

として捉える。

第1回では、第2回以降のテスト設計技法に入る前に、
テスト担当者としての基本的な考え方を扱う。

# よくある誤解

ソフトウェアテストは、次のような作業だと思われがち。

- 画面を操作する
- 手順書どおりに確認する
- OK / NG を記録する
- バグを見つける
- リリース前に最後の確認をする

これらはテスト活動の一部ではある。  
でも、**テストの本質そのものではない**。

---

# この講義でのテストの定義

> ソフトウェアテストとは、  
> 対象の品質やリスクについて判断するために、  
> 情報を集める活動である。

テストは、合格印を押す作業ではない。

関係者が判断するための材料を提供する活動である。

---

# テストが支援する判断

テストは、次のような判断を支援する。

- この機能はリリースしてよいか
- 重大な問題は残っていないか
- どこにリスクがあるか
- 追加で確認すべきことは何か
- 仕様や実装に見落としはないか

**テスト結果は、意思決定の材料になる。**

---

# テストの主な目的

| 目的 | 内容 |
|---|---|
| 欠陥を見つける | 仕様・設計・実装などの問題を発見する |
| 品質状態を把握する | 対象が期待を満たしているか確認する |
| リスクを下げる | 本番で重大問題が出る可能性を減らす |
| 意思決定を支援する | リリース可否や追加対応の判断材料を出す |
| 仕様理解を深める | 曖昧さ・矛盾・未定義に気づく |

---

# 「バグを見つける」だけでは不十分

バグが見つからなかった場合でも、次の情報には価値がある。

- どの範囲を確認したか
- どの条件で確認したか
- どの範囲は確認していないか
- どのリスクが残っているか
- どの程度、安心してよいか

**テストの成果は、バグ件数だけではない。**

---

# 全部テストできない理由

ソフトウェアには、多くの組み合わせが存在する。

例：ログイン機能

- ユーザーIDが正しい / 誤っている
- パスワードが正しい / 誤っている
- アカウントが有効 / 無効
- ロックされている / されていない
- 権限がある / ない
- ブラウザや端末が異なる
- 通信状態が異なる

全部を組み合わせると、ケース数はすぐに膨大になる。

---

# 入力値も膨大になる

例：パスワード入力

- 空欄
- 7文字
- 8文字
- 20文字
- 21文字
- 英字のみ
- 数字のみ
- 記号あり
- 全角文字
- 前後にスペース
- 非常に長い文字列

すべての値を試すことは現実的ではない。

---

# だから、選ぶ必要がある

テスト設計では、次の判断が必要になる。

- 何を重点的に確認するか
- 何を簡易確認にするか
- 何を今回の対象外にするか
- どのリスクを残すか
- 残したリスクを誰にどう伝えるか

**テストは、できるだけ多く確認する活動ではない。**  
**限られた時間で、価値の高い確認を選ぶ活動である。**

---

# テスト担当者に必要な3つの思考

| 思考 | 意味 |
|---|---|
| 疑う | 仕様や実装をそのまま信じすぎない |
| 分解する | 条件・入力・状態・権限・データに分ける |
| 観察する | 起きたことを正確に見て、記録する |

この3つが、テスト設計と欠陥報告の土台になる。

---

# 疑う

疑うとは、誰かを責めることではない。

次のように問いを立てること。

- この仕様で利用者は困らないか
- 例外的な操作はどうなるか
- 想定外の入力ではどうなるか
- 権限が違うユーザーではどうなるか
- 途中で処理が失敗したらどうなるか
- 仕様に書かれていない条件はないか

**攻撃的な疑いではなく、静かな違和感を拾う力。**

---

# 分解する

「ユーザー登録機能」を、そのまま大きな塊として見ない。

分解すると、確認すべきことが見えやすくなる。

- 入力項目
- 必須チェック
- 文字数チェック
- 形式チェック
- 重複チェック
- 登録処理
- 登録後の画面表示
- 登録後のデータ状態
- メール通知
- 権限
- エラー処理

---

# 観察する

悪い記録：

```text
エラーになった。
```

良い記録：

```text
登録ボタン押下後、
「メールアドレスは既に使用されています」
というエラーメッセージが表示された。
画面遷移は発生せず、入力値は保持された。
```

**何が起きたかを、具体的に言語化する。**

---

# テストタイプ

この講義では、最低限この3つを押さえる。

| テストタイプ | 何を見るか | 例 |
|---|---|---|
| 機能テスト | 仕様どおりに機能するか | 登録、検索、申請、承認 |
| 非機能テスト | 機能以外の品質 | 性能、権限、使いやすさ、信頼性 |
| 回帰テスト | 変更で既存機能が壊れていないか | 修正後の周辺確認 |

---

# 機能テスト

機能テストは、対象が仕様どおりの機能を提供しているかを確認する。

例：

- ユーザー登録できる
- ログインできる
- 検索できる
- 申請できる
- 承認できる
- 帳票を出力できる

「その機能が、期待された振る舞いをするか」を見る。

---

# 非機能テスト

非機能テストは、機能そのもの以外の品質を見る。

例：

- 応答時間は許容範囲か
- 大量データでも処理できるか
- 権限のないユーザーが操作できないか
- エラーメッセージは理解しやすいか
- 障害時に安全に復旧できるか

今回は詳細には踏み込まない。  
ただし、**非機能も重要なテスト観点である**。

---

# 回帰テスト

回帰テストは、変更によって既存機能が壊れていないかを確認するテスト。

例：

- 不具合修正後に、修正箇所の周辺を確認する
- 共通部品を変更したため、複数画面を確認する
- パスワード仕様変更後に、登録・変更・リセットを確認する

回帰テストは、**全部やり直すことではない**。  
影響がありそうな範囲を考えて決める。

---

# テスト観点とは

テスト観点とは、テスト対象を見るときの切り口である。

仕様を読んで、いきなりテストケースを書かない。

まずは、

**どのような観点で確認すべきか**

を考える。

---

# 主なテスト観点

| 観点 | 確認例 |
|---|---|
| 入力値 | 空欄、最大値、最小値、不正値 |
| 出力結果 | 表示内容、計算結果、帳票内容 |
| 状態 | 下書き、申請中、承認済み |
| 権限 | 一般ユーザー、管理者、承認者 |
| 操作順序 | 戻る、再読み込み、二重クリック |
| データ更新 | 登録、更新、削除、履歴 |
| エラー処理 | 入力エラー、通信エラー、権限エラー |
| 回帰影響 | 変更箇所、共通処理、周辺機能 |

---

# テスト観点を持つ意味

テスト観点を持つことで、次の効果がある。

- 確認漏れを減らせる
- 仕様を構造的に読める
- テスト条件を整理しやすくなる
- レビューしやすくなる
- テスト設計の意図を説明しやすくなる

白紙から考えるより、観点を使って読む方が強い。  
白紙は、初心者にはだいたい崖に見える。

---

# トレーサビリティとは

トレーサビリティとは、仕様、テスト条件、テストケース、実行結果、欠陥をつなげて追跡できるようにすること。

```text
仕様項目
  ↓
テスト条件
  ↓
テストケース
  ↓
実行結果
  ↓
欠陥報告
```

---

# トレーサビリティがないと困ること

- どの仕様を確認したのかわからない
- どのテストケースがどの仕様に対応しているかわからない
- 仕様変更時に、どのテストを直すべきかわからない
- 不具合がどの要件に関係するかわからない
- テスト漏れを説明できない

テストでは、**何に基づいて何を確認したのか**が重要である。

---

# 仕様項目とテスト条件

例：仕様項目

```text
パスワードは8文字以上20文字以下で入力できる。
```

ここから、複数のテスト条件を抽出できる。

| テスト条件 | 意図 |
|---|---|
| 7文字のパスワードはエラーになる | 下限未満 |
| 8文字のパスワードは登録できる | 下限値 |
| 20文字のパスワードは登録できる | 上限値 |
| 21文字のパスワードはエラーになる | 上限超過 |
| 空欄の場合はエラーになる | 必須入力 |

---

# 仕様項目・テスト条件・テストケース

| 種別 | 内容 |
|---|---|
| 仕様項目 | システムが満たすべき内容 |
| テスト条件 | その仕様を確認するための観点・条件 |
| テストケース | 実行できる具体的な手順と期待結果 |

流れとしては、次のように考える。

```text
仕様項目
  ↓
テスト観点
  ↓
テスト条件
  ↓
テストケース
```

---

# ミニワーク

次の仕様を読み、テスト観点とテスト条件を考える。

```text
ユーザーはメールアドレスとパスワードを入力してログインできる。
パスワードは8文字以上20文字以下とする。
ログインに5回失敗した場合、アカウントをロックする。
ロックされたアカウントではログインできない。
```

考えること：

- テスト観点
- テスト条件
- 仕様として確認したい不明点

---

# ミニワーク：記入例

| 作業 | 内容 |
|---|---|
| テスト観点 | 入力値、認証、エラー処理、ロック、状態、表示、回帰 |
| テスト条件 | 正しい情報でログインできる / 5回失敗でロックされる / ロック済みではログインできない |
| 不明点 | ロック解除方法はあるか / 失敗回数はいつリセットされるか |

まずは正解を探すより、**確認すべきことを分解して出す**ことが目的。

---

# 回答例：テスト条件

| No | テスト条件 |
|---:|---|
| 1 | 正しいメールアドレスと正しいパスワードでログインできる |
| 2 | 存在しないメールアドレスではログインできない |
| 3 | 正しいメールアドレスと誤ったパスワードではログインできない |
| 4 | パスワードが7文字の場合はエラーになる |
| 5 | パスワードが8文字の場合は入力条件を満たす |
| 6 | ログイン失敗が4回まではロックされない |
| 7 | ログイン失敗が5回に達したらロックされる |
| 8 | ロック済みアカウントでは正しいパスワードでもログインできない |

---

# 回答例：不明点

| No | 不明点 |
|---:|---|
| 1 | ロック後、解除方法はあるか |
| 2 | 失敗回数はいつリセットされるか |
| 3 | メールアドレスの形式チェックはあるか |
| 4 | エラーメッセージは、ID誤りとパスワード誤りで同じか |
| 5 | ロック状態は管理者画面などで確認できるか |
| 6 | ロック時に通知メールは送信されるか |

仕様を読んで問いを立てることも、テスト担当者の重要な仕事である。

---

# 今日のまとめ

- テストは、品質に関する判断材料を集める活動である
- すべてをテストすることはできない
- テスト担当者には、疑う・分解する・観察する思考が必要
- テストには、機能・非機能・回帰などのタイプがある
- テスト観点を持つことで、確認漏れを減らせる
- 仕様項目とテスト条件は異なる
- テストケースを書く前に、まず何を確認すべきかを整理する
