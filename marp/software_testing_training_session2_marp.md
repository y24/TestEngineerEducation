# 第2回  
# テスト設計技法とシナリオテスト設計

未経験者向け ソフトウェアテスト基礎講座

---

# 今日の位置づけ

第1回では、次を扱った。

- テストの目的
- 全部テストできない理由
- テスト観点
- 仕様項目とテスト条件の違い

第2回では、抽出したテスト条件を、  
**テストケースやシナリオテストに落とし込む方法**を扱う。

---

# 今日の中心テーマ

テスト設計は、入力値の確認だけではない。

実際の利用者は、単独の項目を確認するためではなく、  
**何らかの目的を達成するため**にシステムを使う。

今日の柱は2つ。

| 柱 | 内容 |
|---|---|
| 条件をケース化する技術 | 同値分割・境界値分析、デシジョンテーブル |
| 流れをシナリオ化する技術 | ユーザーストーリー抽出、成功・代替・例外シナリオ |

---

# 今日のゴール

今日の終了時点で、次のことを説明・実践できる状態を目指す。

- テスト条件からテストケースを作れる
- 同値分割・境界値分析の考え方を使える
- デシジョンテーブルで条件の組み合わせを整理できる
- ユーザーストーリーを抽出できる
- 成功・代替・例外シナリオを区別できる
- エラー推測と探索的テストの基本を説明できる
- 良いテストケースの条件を説明できる

# 第1回の復習

仕様から、いきなりテストケースを書くのではなく、  
まずテスト観点とテスト条件を整理する。

```text
仕様項目
  ↓
テスト観点
  ↓
テスト条件
  ↓
テストケース / シナリオテスト
```

第2回では、最後の変換を扱う。

---

# 例：仕様項目からテスト条件へ

仕様：

```text
パスワードは8文字以上20文字以下で入力できる。
```

抽出できるテスト条件：

| テスト条件 | 意図 |
|---|---|
| 7文字のパスワードはエラーになる | 下限未満の確認 |
| 8文字のパスワードは登録できる | 下限値の確認 |
| 20文字のパスワードは登録できる | 上限値の確認 |
| 21文字のパスワードはエラーになる | 上限超過の確認 |

---

# テスト条件とテストケースの違い

テスト条件は、**何を確認するか**を表す。  
テストケースは、**どのように確認するか**を表す。

| 種別 | 例 |
|---|---|
| テスト条件 | 7文字のパスワードはエラーになる |
| テストケース | パスワード欄に7文字の値を入力し、登録ボタンを押す。エラーメッセージが表示され、登録されないことを確認する |

テスト条件は確認対象。  
テストケースは実行手順。

---

# テストケースに必要な要素

良いテストケースには、最低限次の要素が必要。

| 要素 | 内容 |
|---|---|
| 前提条件 | 実行前に必要な状態 |
| 入力値・テストデータ | 使用する具体的な値 |
| 操作手順 | 実行する操作 |
| 期待結果 | 本来どうなるべきか |
| 確認観点 | 何を確認するためのケースか |

**期待結果は、観察できる形で書く。**

---

# ケース化の例

| 項目 | 内容 |
|---|---|
| 前提条件 | ユーザー登録画面を表示している |
| 入力値 | パスワードに7文字の値 `abc1234` を入力する |
| 手順 | 必須項目を入力し、登録ボタンを押す |
| 期待結果 | パスワード文字数エラーが表示され、登録処理は行われない |
| 確認観点 | パスワード下限未満の入力制御 |

「正しく動く」「エラーになる」だけでは弱い。  
**何が表示され、何が起きないか**まで書く。

---

# 同値分割・境界値分析

入力値や範囲条件を扱うときに使いやすい。

例：

- 1文字以上20文字以下
- 0円以上100,000円以下
- 開始日は終了日以前
- 数量は1以上999以下
- 添付ファイルは10MB以下
- パスワードは8文字以上20文字以下

全部の値は試せない。  
だから、**代表値と境界値を選ぶ**。

---

# 同値分割とは

同じように扱われる値をグループに分ける考え方。

仕様：

```text
金額は1円以上100,000円以下で入力できる。
```

| 区分 | 値の範囲 | 種別 |
|---|---:|---|
| 1円未満 | 0円など | 無効 |
| 1円〜100,000円 | 50,000円など | 有効 |
| 100,001円以上 | 100,001円など | 無効 |

すべての値ではなく、同じ意味を持つ範囲から代表値を選ぶ。

---

# 境界値分析とは

範囲の端に注目する考え方。

不具合は、範囲の中央よりも境界付近で起きやすい。

| 観点 | 確認値 | 期待 |
|---|---:|---|
| 下限未満 | 0円 | エラー |
| 下限 | 1円 | 入力可 |
| 有効範囲内 | 50,000円 | 入力可 |
| 上限 | 100,000円 | 入力可 |
| 上限超過 | 100,001円 | エラー |

---

# 同値分割・境界値分析のポイント

- 全部の値を試すのではなく、代表値を選ぶ
- 有効な値だけでなく、無効な値も確認する
- 範囲の境界付近を重点的に見る
- 「以上」「以下」「未満」「より大きい」に注意する

覚え方は、まずこれで十分。

> 範囲がある仕様では、範囲の中・外・境目を見る。

---

# デシジョンテーブル

複数条件の組み合わせによって結果が変わる場合に使う。

例：

- 会員種別と購入金額で割引率が変わる
- ユーザー権限と申請状態で操作可否が変わる
- 入力状態と承認状態でボタンの表示が変わる
- アカウント状態と認証結果でログイン可否が変わる

複数条件を頭の中だけで考えると、漏れや矛盾が起きやすい。

---

# デシジョンテーブルの例

仕様：

```text
ユーザーID、パスワードが正しく、
アカウントがロックされていない場合にログインできる。
```

| 条件 / ルール | R1 | R2 | R3 | R4 |
|---|---:|---:|---:|---:|
| ユーザーIDが正しい | Y | Y | N | N |
| パスワードが正しい | Y | N | Y | N |
| アカウントがロックされていない | Y | Y | Y | Y |
| ログイン成功 | Y | N | N | N |
| エラー表示 | N | Y | Y | Y |

---

# ロック状態を含めた例

| 条件 / ルール | R1 | R2 | R3 | R4 | R5 |
|---|---:|---:|---:|---:|---:|
| ユーザーIDが正しい | Y | Y | Y | N | - |
| パスワードが正しい | Y | Y | N | - | - |
| アカウントがロックされていない | Y | N | Y | Y | N |
| ログイン成功 | Y | N | N | N | N |
| ロックエラー | N | Y | N | N | Y |
| 認証エラー | N | N | Y | Y | N |

`-` は、その条件が結果に影響しない、または確認しなくてよいことを表す。

---

# デシジョンテーブルの利点

- 条件の組み合わせ漏れに気づきやすい
- 仕様の矛盾に気づきやすい
- 期待結果を整理しやすい
- レビューしやすい
- テストケース化しやすい

業務システムでは、権限、状態、金額、区分、承認状況など、  
複数条件が絡むことが多い。

**条件が増えたら、頭の中ではなく表で考える。**

---

# シナリオテストとは

シナリオテストとは、利用者が目的を達成するまでの  
**一連の流れ**を確認するテストである。

| 種別 | 見るもの | 例 |
|---|---|---|
| 単発のテストケース | 個別条件や個別機能 | 金額100,001円でエラーになる |
| シナリオテスト | 利用者の目的達成までの流れ | 経費申請を作成し、上長に申請し、承認される |

単発ケースは条件確認。  
シナリオテストは流れの確認。

---

# なぜシナリオテストが必要か

個別機能が正しく動いていても、  
利用者の目的が達成できないことがある。

- 申請はできるが、承認者の一覧に表示されない
- 登録はできるが、登録後の検索で見つからない
- 下書き保存はできるが、再編集できない
- 承認はできるが、承認後のステータスが更新されない
- 帳票は出力できるが、後続業務で必要な項目が不足している

**単一画面だけを見ていると、流れの不具合を見落とす。**

---

# ユーザーストーリーとは

利用者が何をしたいのかを表す短い記述。

基本形：

```text
＜利用者＞として、
＜目的＞したい。
それは＜価値＞のためである。
```

例：

```text
申請者として、
経費申請を提出したい。
それは、承認後に精算してもらうためである。
```

---

# ユーザーストーリーの例

```text
承認者として、
提出された経費申請を確認し、承認または差戻ししたい。
それは、誤った支払いを防ぐためである。
```

```text
管理者として、
ユーザーの権限を変更したい。
それは、担当業務に応じた操作範囲を設定するためである。
```

ユーザーストーリーを使うと、システムを  
**画面や項目の集合ではなく、利用者の目的を支えるもの**として見られる。

---

# ユーザーストーリーからシナリオへ

```text
ユーザー
  ↓
目的
  ↓
開始条件
  ↓
操作の流れ
  ↓
終了条件
  ↓
成功・代替・例外シナリオ
```

流れを考えるときは、  
「何をしたら終わりか」「状態はどう変わるか」まで見る。

---

# シナリオ展開の例

ユーザーストーリー：

```text
申請者として、経費申請を提出したい。
それは、承認後に精算してもらうためである。
```

| 種別 | シナリオ |
|---|---|
| 成功 | 必須項目を入力し、経費申請を提出する |
| 代替 | 途中で下書き保存し、後で再編集して提出する |
| 代替 | 添付ファイルなしで申請する |
| 例外 | 必須項目未入力で申請しようとする |
| 例外 | 金額上限を超えて申請しようとする |
| 例外 | 申請後に編集しようとする |

---

# 成功・代替・例外シナリオ

シナリオは、正常な流れだけではない。

| 種別 | 内容 |
|---|---|
| 成功シナリオ | 利用者が通常どおり目的を達成する流れ |
| 代替シナリオ | 通常とは異なるが、許容される流れ |
| 例外シナリオ | エラー、中断、失敗、不正操作などの流れ |

失敗、寄り道、やり直し、中断、権限違いもシナリオとして考える。

---

# シナリオ抽出の観点

| 観点 | 問い |
|---|---|
| 利用者 | 誰が使うのか |
| 目的 | 何を達成したいのか |
| 開始条件 | どの状態から始まるのか |
| 終了条件 | 何ができたら成功なのか |
| 主経路 | 通常はどのような流れか |
| 代替経路 | 別の進み方はあるか |
| 例外経路 | 失敗、中断、エラーはあるか |
| 状態変化 | データやステータスはどう変わるか |
| 権限 | 誰ならできて、誰ならできないか |
| 後続影響 | 次の業務や機能に影響するか |

---

# シナリオテスト設計の成果物例

| ID | ユーザーストーリー | シナリオ | 種別 | 確認したいこと |
|---|---|---|---|---|
| US-01-S01 | 申請者として経費申請を提出したい | 必須項目を入力して申請する | 成功 | 状態が「申請中」になる |
| US-01-S02 | 同上 | 下書き保存して後で再編集する | 代替 | 下書き状態で保存され、再編集できる |
| US-01-S03 | 同上 | 必須項目未入力で申請する | 例外 | エラーが表示され、状態が変わらない |
| US-01-S04 | 同上 | 金額上限を超えて申請する | 例外 | 金額エラーが表示され、申請されない |

---

# エラー推測とは

過去の経験や対象システムの特徴から、  
**欠陥がありそうな場所**を考える技法。

ただの思いつきではなく、次の情報をもとに考える。

- 過去に起きた不具合
- 仕様の曖昧な部分
- 複雑な条件分岐
- 例外的な操作
- 利用者が間違えやすい操作
- データの境界
- 外部連携やファイル出力
- 権限や状態の切り替わり

---

# エラー推測の例

| 観点 | 例 |
|---|---|
| 入力 | 空欄、最大文字数、全角半角、前後スペース、記号 |
| 操作 | 二重クリック、戻る、再読み込み、途中離脱 |
| 状態 | 削除済み、ロック済み、承認済み、期限切れ |
| 権限 | 権限不足、権限変更直後、別ユーザーのデータ |
| データ | 重複、存在しないコード、古いデータ、大量データ |
| 連携 | メール送信失敗、API失敗、ファイル出力失敗 |

現実の利用者は、仕様書の読者ではない。  
わりと自由に動く。

---

# 探索的テストとは

探索的テストとは、テストの実行、観察、学習、次のテスト設計を  
同時に進めるテストである。

ただし、**自由に触ること**ではない。

| 要素 | 内容 |
|---|---|
| チャーター | 今回、何を探るか |
| 操作 | 実際に試したこと |
| 観察 | 気づいたこと |
| 仮説 | なぜそうなったと考えるか |
| 記録 | 再現できるように残すこと |

---

# 探索的テストの例

```text
チャーター：
経費申請の作成から提出までの流れで、
入力エラーや状態不整合が起きないかを探る。

観察：
金額上限超過では画面上にエラーが出るが、
添付ファイル容量超過ではサーバーエラー画面に遷移した。

仮説：
入力値チェックとファイルチェックで、
エラー処理の実装方針が異なっている可能性がある。
```

目的を決め、観察し、気づいたことを次の確認につなげる。

---

# 悪いテストケースの例

| 項目 | 内容 |
|---|---|
| 手順 | 正しい値を入力して登録する |
| 期待結果 | 正常に登録される |

問題点：

- 正しい値が何か不明
- 前提条件が不明
- どの画面で操作するのか不明
- 期待結果が曖昧
- 何を確認するためのケースか不明
- どこで登録結果を確認するのか不明

---

# 良いテストケースの例

| 項目 | 内容 |
|---|---|
| 確認観点 | パスワード下限値でユーザー登録できること |
| 前提条件 | ユーザー登録画面を表示している。`test001@example.com` は未登録 |
| 入力値 | メールアドレス：`test001@example.com`、パスワード：`abcd1234` |
| 手順 | 必須項目を入力し、登録ボタンを押す |
| 期待結果 | 登録完了メッセージが表示される |
| 後続確認 | ユーザー一覧に `test001@example.com` が表示される |

実行者が変わっても、同じ確認がしやすい。

---

# シナリオテストケースの例

| 項目 | 内容 |
|---|---|
| 確認観点 | 経費申請を提出すると、状態が「申請中」になり、承認者の一覧に表示されること |
| 前提条件 | 申請者ユーザーでログインしている。承認者が設定済みである |
| 入力値 | 件名：交通費精算、金額：10,000円、利用日：当月内の日付、支払先：A交通 |
| 手順 | 経費申請画面を開き、必要項目を入力して申請ボタンを押す |
| 期待結果 | 申請完了メッセージが表示され、状態が「申請中」になる |
| 後続確認 | 承認者ユーザーでログインし、承認待ち一覧に対象申請が表示される |

---

# 良いテストケースの条件

- 目的や確認観点が明確である
- 前提条件が明確である
- 入力値が具体的である
- 操作手順が再現できる
- 期待結果が観察可能である
- 後続確認が必要な場合、それが書かれている
- 誰が実行しても同じ判断ができる
- 仕様やテスト条件との対応が追える

テストケースは、実行者への作業指示であり、  
**設計意図を残す文書**でもある。

---

# ミニワーク：題材

次の仕様を読み、ユーザーストーリー、シナリオ、テストケースを考える。

```text
ユーザーは経費申請を作成できる。
申請には、件名、金額、利用日、支払先を入力する。
金額は1円以上100,000円以下とする。
申請者は下書き保存または申請ができる。
申請後、承認者が承認または差戻しできる。
差戻された申請は、申請者が修正して再申請できる。
承認済みの申請は、申請者が編集できない。
```

---

# ミニワーク：作業内容

| 作業 | 内容 |
|---|---|
| ユーザーストーリー | 利用者、目的、価値を整理する |
| シナリオ | 成功、代替、例外シナリオを挙げる |
| 境界値 | 金額の確認値を挙げる |
| デシジョンテーブル | 操作可否や結果が変わる条件を整理する |
| テストケース | 代表シナリオを1件、具体的なケースに落とす |

時間が短い場合は、グループで分担してもよい。

---

# 回答例：ユーザーストーリー

| ID | ユーザーストーリー |
|---|---|
| US-01 | 申請者として、経費申請を提出したい。それは、承認後に精算してもらうためである |
| US-02 | 承認者として、提出された経費申請を承認または差戻ししたい。それは、申請内容の妥当性を確認するためである |
| US-03 | 申請者として、差戻された申請を修正して再申請したい。それは、誤りを直して承認を受けるためである |

---

# 回答例：シナリオ

| ID | 種別 | シナリオ | 確認したいこと |
|---|---|---|---|

# まとめ

第2回では、テスト条件をテストケースやシナリオに落とし込む方法を扱った。

- テスト条件は「何を確認するか」
- テストケースは「どう確認するか」
- 同値分割・境界値分析では、範囲の中・外・境目を見る
- デシジョンテーブルでは、複数条件の組み合わせを表で整理する
- シナリオテストでは、利用者の目的達成までの流れを見る

# 次回扱うこと

第3回では、作成したテストケースやシナリオに対して、次を扱う。

- どこを優先して確認するか
- どこまで回帰テストするか
- どこをテストしないか
- 欠陥をどう報告するか
- 進捗をどう報告するか

つまり、**テスト設計を現場判断と報告につなげる回**になる。
