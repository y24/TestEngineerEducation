# テストでは「全部」はできない

テスト対象には、多くの条件・状態・データ・環境がある。  
さらに、テストに使える時間と人員には制約がある。

だから、テストでは次の判断が必要になる。

- 何を重点的に確認するか
- 何を代表確認にするか
- 何を今回は確認しないか
- どのリスクを残すか
- 残したリスクを誰にどう伝えるか

---

# リスクとは

リスクとは、将来起こる可能性があり、起きた場合に悪い影響を与えるもの。

テストでは、大きく2種類のリスクを考える。

| 種別 | 内容 |
|---|---|
| プロダクトリスク | 製品・システムそのものに関するリスク |
| プロジェクトリスク | 開発・テスト活動の進め方に関するリスク |

---

# プロダクトリスク

プロダクトリスクは、製品が利用者や業務に悪影響を与えるリスク。

| リスク | 影響 |
|---|---|
| 金額計算が誤る | 誤請求・誤精算・会計不整合が発生する |
| 権限のないユーザーが操作できる | 情報漏えい・不正操作につながる |
| 申請状態が正しく更新されない | 後続業務が止まる |
| 帳票に誤った値が出力される | 顧客・監査・業務判断に影響する |
| データが保存されない | 利用者の作業が失われる |

---

# プロジェクトリスク

プロジェクトリスクは、テスト活動や開発活動がうまく進まないリスク。

| リスク | 影響 |
|---|---|
| 仕様が未確定 | テスト設計がやり直しになる |
| テスト環境が不安定 | 実行が進まない、結果が信用できない |
| テストデータが不足している | 必要な条件を確認できない |
| 担当者のスキルが不足している | 見落としや報告品質低下につながる |
| 開発遅延でテスト期間が短い | 確認範囲を削る必要が出る |

---

# 2種類のリスクの使い分け

| 種別 | 簡単な言い方 | 主な使いどころ |
|---|---|---|
| プロダクトリスク | 製品が壊れるリスク | テストの厚み・優先順位を決める |
| プロジェクトリスク | テスト活動が進まないリスク | 進め方・報告・完了判断に使う |

テスト担当者は、プロダクトリスクを見て確認内容を考え、  
プロジェクトリスクを見て進め方や報告内容を考える。

---

# 重要度・発生可能性・優先度

この3つは混同しやすい。

| 用語 | 意味 |
|---|---|
| 重要度・影響度 | 問題が起きたときのダメージの大きさ |
| 発生可能性 | 問題が起きそうな度合い |
| 優先度 | 今どれを先に確認・対応すべきか |

優先度は、影響度だけでも、発生可能性だけでも決まらない。

---

# 重要度・影響度の例

影響度が高い例。

- 金額や数量の誤計算
- データ破壊
- 情報漏えい
- 権限不備
- 業務停止
- リリース後に回復が難しい不具合
- 顧客や監査に影響する誤表示

会計・業務系システムでは、数値・帳票・状態・権限の影響度は高くなりやすい。

---

# 発生可能性の例

発生可能性が高い例。

- 変更量が大きい
- 仕様が複雑
- 条件分岐が多い
- 過去に不具合が多い
- 担当者が不慣れ
- 共通部品を変更している
- 外部連携や非同期処理がある
- 手作業の設定やデータ移行がある

「変更がないから絶対安全」とは言えない。

---

# 優先度の考え方

| 対象 | 影響度 | 発生可能性 | 優先度 | 理由 |
|---|---|---|---|---|
| 金額計算 | 高 | 中 | 高 | 誤りが業務に大きく影響する |
| 権限チェック | 高 | 中 | 高 | 情報漏えいや不正操作につながる |
| 申請状態更新 | 高 | 中 | 高 | 後続業務が止まる |
| 表示文言 | 低 | 中 | 低 | 業務影響が小さい |
| 画面レイアウト | 中 | 高 | 中 | 操作性に影響する |

---

# リスク評価の簡易表

新人向けには、まず3段階で十分。

| 影響度 | 発生可能性 | 優先度の考え方 |
|---|---|---|
| 高 | 高 | 最優先で確認する |
| 高 | 中 | 重点的に確認する |
| 高 | 低 | 代表ケースや重要ケースを確認する |
| 中 | 高 | 変更箇所・周辺を確認する |
| 中 | 中 | 通常の確認対象 |
| 低 | 低 | 簡易確認、または対象外候補 |

これは正解表ではなく、会話の道具。

---

# テストしない判断

テストでは、すべてを確認できない。  
そのため、現場では次の判断が必要になる。

- 今回は確認しない
- 代表ケースだけ確認する
- 別フェーズで確認する
- 自動テストやレビューで代替する

大事なのは、**テストしないこと自体が悪いのではなく、理由なく見落とすことが悪い**ということ。

---

# テストしない判断に必要な情報

| 項目 | 内容 |
|---|---|
| 対象 | 何をテストしないのか |
| 理由 | なぜ今回確認しないのか |
| 影響 | 問題があった場合に何が起きるか |
| 代替策 | 他の確認方法があるか |
| 残存リスク | 何が未確認として残るか |
| 判断者 | 誰が了承したか |

「なんとなく時間がないからやらない」は、判断として弱い。

---

# テストしない判断の例

| 対象 | 判断 | 理由 | 残存リスク |
|---|---|---|---|
| 変更されていないヘルプ画面 | 対象外 | 今回の修正影響がない | 既存不具合は検出できない |
| 管理者向け低頻度機能 | 代表ケースのみ | 利用頻度が低く、変更影響も限定的 | 例外条件の不具合が残る可能性 |
| 外部サービス障害時の詳細挙動 | 対象外 | 検証環境で再現困難 | 障害時表示に問題が残る可能性 |
| 古いブラウザ | 対象外 | サポート対象外 | 対象外環境での動作は保証しない |

---

# 回帰テストとは

回帰テストは、変更によって既存機能が壊れていないかを確認するテスト。

不具合修正や機能追加では、変更箇所だけでなく、周辺機能や共通処理に影響が出ることがある。

回帰テストは、**全部やり直すことではない**。  
変更の影響を考え、必要な範囲を決める活動。

---

# 回帰範囲を考える観点

| 観点 | 確認すること |
|---|---|
| 変更箇所 | 直接修正された機能 |
| 周辺機能 | 変更箇所とつながる機能 |
| 共通部品 | 共通処理、共通画面、共通API、共通ライブラリ |
| 同じデータ | 同じテーブル、同じマスタ、同じファイルを使う機能 |
| 同じ業務フロー | 前後の業務や後続処理 |
| 権限・状態 | 状態遷移や権限制御に関係する機能 |
| 過去不具合 | 過去に不具合が多かった箇所 |

---

# 回帰範囲の例

変更内容：  
**パスワード最小文字数を8文字から12文字に変更した。**

影響範囲候補：

- ユーザー登録
- ログイン
- パスワード変更
- パスワードリセット
- 管理者による初期パスワード発行
- アカウントロック
- エラーメッセージ
- API経由のパスワード設定

修正は小さく見えても、影はけっこう長い。

---

# 回帰範囲の決め方

```text
1. 何が変更されたかを確認する
2. 変更箇所が使っている部品・データ・設定を確認する
3. 周辺機能や後続業務への影響を考える
4. 影響度と発生可能性を見て優先順位を付ける
5. 確認する範囲、簡易確認にする範囲、対象外を決める
6. 対象外や未確認のリスクを報告する
```

---

# 回帰範囲の記録例

| 対象 | 確認レベル | 理由 |
|---|---|---|
| パスワード変更 | 重点確認 | 直接変更箇所であるため |
| ユーザー登録 | 重点確認 | 同じ入力制約を使うため |
| パスワードリセット | 重点確認 | 同じポリシー適用が必要なため |
| ログイン | 代表確認 | 既存認証への影響確認のため |
| 管理者機能 | 簡易確認 | 初期パスワード発行に影響する可能性 |
| プロフィール編集 | 対象外 | パスワード項目を扱わないため |

---

# 欠陥報告の目的

欠陥報告は、開発者を責めるための文書ではない。  
発生した問題を、再現・調査・修正・判断できるように伝えるための文書。

良い欠陥報告は、次に役立つ。

- 開発者が再現できる
- 原因調査がしやすい
- 修正の優先度を判断できる
- 影響範囲を考えやすい
- 関係者が状況を共有できる

---

# 欠陥報告に必要な項目

| 項目 | 内容 |
|---|---|
| タイトル | 何が起きたか一目でわかる |
| 発生環境 | OS、ブラウザ、バージョン、環境など |
| 前提条件 | データ状態、ユーザー、権限など |
| 再現手順 | 同じ事象を再現できる操作 |
| 期待結果 | 本来どうなるべきか |
| 実績結果 | 実際に何が起きたか |
| 再現率 | 毎回か、ときどきか |
| 証跡 | 画面キャプチャ、ログ、動画、出力ファイルなど |

---

# タイトルの書き方

悪いタイトル：

```text
エラーになる
登録できない
```

良いタイトル：

```text
ユーザー登録で12文字のパスワードを入力しても、文字数エラーとなり登録できない
```

```text
承認済みの経費申請を戻るボタン経由で編集できてしまう
```

何が、どの条件で、どうなるのかが伝わるように書く。

---

# 再現手順

悪い例：

```text
経費申請を登録するとエラーになります。
```

良い例：

```text
1. 申請者ユーザーでログインする
2. 経費申請画面を開く
3. 件名に「交通費精算」を入力する
4. 金額に「100000」を入力する
5. 利用日に当月の日付を入力する
6. 支払先に「A交通」を入力する
7. 申請ボタンを押す
```

再現手順は、操作の地図。

---

# 期待結果と実績結果

悪い例：

```text
エラーになります。
```

良い例：

```text
期待結果：
金額100,000円は上限値として許可されるため、経費申請が提出される。

実績結果：
「金額は1円以上100,000円以下で入力してください」という
エラーメッセージが表示され、申請できない。
```

期待結果が書けない場合、仕様理解が曖昧な可能性がある。

---

# 事実と推測を分ける

悪い例：

```text
たぶんバリデーションがおかしいです。
```

良い例：

```text
実績結果：
申請ボタン押下後、画面上部に
「金額は1円以上100,000円以下で入力してください」と表示される。
申請一覧に対象データは追加されていない。

補足：
上限値100,000円を超過として扱っている可能性がある。
```

観察した事実と原因の推測は分ける。

---

# 重大度と優先度

| 用語 | 意味 |
|---|---|
| 重大度 | 欠陥が製品や業務に与える影響の大きさ |
| 優先度 | どの順番で対応すべきか |

| 欠陥 | 重大度 | 優先度 | 理由 |
|---|---|---|---|
| 金額計算が誤る | 高 | 高 | 業務影響が大きい |
| 管理画面の文言誤り | 低 | 低 | 影響が小さい |
| ロゴが表示されない | 低 | 高 | リリース直前の見た目品質として優先される場合 |

---

# テスト進捗報告の目的

進捗報告の目的は、「どれだけ頑張ったか」を伝えることではない。  
関係者が状況を理解し、必要な判断をできるようにすること。

伝えるべきこと。

- どこまで終わったか
- 結果はどうだったか
- 重大な問題はあるか
- 未実行や保留はあるか
- テストを妨げている問題はあるか
- リリース判断に影響するリスクはあるか

---

# 進捗報告で最低限伝える項目

| 項目 | 内容 |
|---|---|
| 実行状況 | 計画件数、実行済み件数、未実行件数 |
| 結果 | OK、NG、保留、ブロック |
| 欠陥状況 | 新規欠陥、未解決欠陥、重大欠陥 |
| 遅延・阻害要因 | 環境不具合、仕様未確定、データ不足など |
| 残存リスク | 未確認範囲、重大欠陥、対象外範囲 |
| 判断事項 | 続行、延期、範囲変更、追加確認など |

---

# 悪い進捗報告

```text
テストは70%終わりました。
不具合がいくつかあります。
```

これでは、判断が難しい。

- 何件中、何件終わったのか
- NGは何件か
- 重大な欠陥はあるのか
- 未実行の理由は何か
- リリース判断に影響するのか

---

# 良い進捗報告

```text
予定100件中70件を実行済み。
結果はOK 58件、NG 8件、保留4件、未実行30件。

NG 8件のうち、重大度高の欠陥が2件あります。
2件はいずれも金額計算に関係しており、リリース判断に影響します。

未実行30件のうち10件は、テスト環境のデータ不備によりブロックされています。
残り20件は予定どおり明日実行予定です。

現時点では、金額計算まわりの重大欠陥が解消されるまで、完了判断は難しい状態です。
```

---

# 進捗報告テンプレート

```text
テスト進捗：
- 計画件数：
- 実行済み：
- 未実行：
- 進捗率：

結果：
- OK：
- NG：
- 保留：
- ブロック：

主な欠陥：
- 重大度高：
- 重大度中：
- 重大度低：

阻害要因：
-

残存リスク：
-

判断・相談事項：
-
```

# ミニワーク：題材

次の変更内容を読み、リスク、回帰範囲、欠陥報告、進捗報告を考える。

```text
パスワードポリシー変更により、
パスワードの最小文字数を8文字から12文字に変更した。

対象はユーザー登録、パスワード変更、パスワードリセットである。

ただし、リリースまでの時間が短く、
すべての関連機能を詳細に確認する時間はない。
```

---

# ミニワーク：作業内容

| 作業 | 内容 |
|---|---|
| リスク | どのような問題が起きると困るか |
| 優先度 | 何を重点的に確認するか |
| 回帰範囲 | どの機能を確認するか |
| テストしない範囲 | 今回対象外にする範囲と理由 |
| 欠陥報告 | 不具合を1件想定し、報告内容を書く |
| 進捗報告 | テスト途中の状況を報告する |

---

# 回答例：リスクと優先度

| 対象 | リスク | 影響度 | 発生可能性 | 優先度 |
|---|---|---|---|---|
| ユーザー登録 | 12文字未満で登録できてしまう | 高 | 中 | 高 |
| パスワード変更 | 12文字以上でもエラーになる | 高 | 中 | 高 |
| パスワードリセット | 新ポリシーが適用されない | 高 | 中 | 高 |
| ログイン | 既存ユーザーがログインできなくなる | 高 | 低 | 中 |
| エラーメッセージ | 旧仕様の「8文字以上」と表示される | 中 | 中 | 中 |

---

# 回答例：回帰テスト範囲

| 対象 | 確認レベル | 理由 |
|---|---|---|
| ユーザー登録 | 重点確認 | 直接対象機能であるため |
| パスワード変更 | 重点確認 | 直接対象機能であるため |
| パスワードリセット | 重点確認 | 直接対象機能であるため |
| ログイン | 代表確認 | 既存ユーザーへの影響確認のため |
| エラーメッセージ | 代表確認 | 利用者案内に影響するため |
| 管理者機能 | 簡易確認 | 関連機能である可能性があるため |
| プロフィール編集 | 対象外 | パスワードを扱わないため |

---

# 回答例：テストしない範囲

| 対象 | 判断 | 理由 | 残存リスク |
|---|---|---|---|
| サポート対象外ブラウザ | 対象外 | 対応範囲外のため | 対象外環境での動作は未確認 |
| プロフィール編集 | 対象外 | パスワード項目を扱わないため | 間接影響があった場合は検出できない |
| 管理者機能の詳細パターン | 簡易確認のみ | 利用頻度と時間制約を踏まえたため | 例外条件の不具合が残る可能性 |

```text
新規ユーザー登録に影響するため、リリース判断に関係します。

未実行6件のうち、2件はパスワードリセットメールが送信されない
環境不具合によりブロックされています。
残り4件は本日中に実行予定です。

現時点では、ユーザー登録の重大欠陥が解消されるまで、
パスワードポリシー変更部分の完了判断は難しい状態です。
```

# 第3回のまとめ

- プロダクトリスクは、製品や業務に悪影響を与えるリスク
- プロジェクトリスクは、テスト活動や開発活動が進まないリスク
- 重要度・発生可能性・優先度は分けて考える
- すべてを同じ厚さで確認することはできない
- テストしない判断には、理由と残存リスクが必要
- 回帰テストでは、変更箇所だけでなく周辺・共通・後続を見る
- 欠陥報告では、再現手順・期待結果・実績結果を明確に分ける
- 進捗報告では、件数だけでなく判断材料を伝える
