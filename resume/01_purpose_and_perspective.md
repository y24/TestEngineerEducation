# 第1回 レジュメ

## ソフトウェアテストの目的とテスト観点

## 1. 講義の位置づけ

この講義では、ソフトウェアテストを「画面を操作して結果を確認する作業」としてではなく、**品質に関する判断材料を集める専門的な活動**として捉える。

第1回では、テスト設計の前提となる考え方を扱う。
具体的には、テストの目的、全部テストできない理由、テスト担当者に必要な思考、テスト観点、テスト条件の考え方を学ぶ。

第2回以降で扱うテスト設計技法やシナリオテスト設計の土台になる回。

| 仕様項目とテスト条件を区別できる  | 仕様に書かれていることと、確認すべきことを分けて考えられる       |

# 4. 導入：テストとは何か

## 4.1 よくある誤解

ソフトウェアテストは、単に次のような作業だと思われがちである。

* 画面を操作する
* 手順書どおりに確認する
* OK / NG を記録する
* バグを見つける
* リリース前に最後の確認をする

これらはテスト活動の一部ではあるが、テストの本質そのものではない。

## 4.2 この講義での定義

この講義では、ソフトウェアテストを次のように捉える。

> ソフトウェアテストとは、対象の品質やリスクについて判断するために、情報を集める活動である。

テストは「合格印を押す作業」ではない。
むしろ、関係者が次のような判断をするための材料を提供する活動である。

* この機能はリリースしてよいか
* 重大な問題は残っていないか
* どこにリスクがあるか
* 追加で確認すべきことは何か
* 仕様や実装に見落としはないか

# 5. テストの目的

## 5.1 テストの主な目的

テストには複数の目的がある。

| 目的        | 内容                            |
| --------- | ----------------------------- |
| 欠陥を見つける   | 仕様、設計、実装、データ、環境などに含まれる問題を発見する |
| 品質状態を把握する | 対象がどの程度期待を満たしているかを確認する        |
| リスクを下げる   | 本番環境や利用者に重大な問題が出る可能性を減らす      |
| 意思決定を支援する | リリース可否や追加対応の判断材料を提供する         |
| 仕様理解を深める  | 仕様の曖昧さ、矛盾、未定義部分に気づく           |

## 5.2 「バグを見つける」だけでは不十分

バグを見つけることは重要だが、それだけではテストの価値を十分に説明できない。

たとえば、バグが見つからなかった場合でも、次のような情報には価値がある。

* どの範囲を確認したか
* どのような条件で確認したか
* どの範囲は確認していないか
* どのリスクが残っているか
* どの程度、安心してよいか

つまり、テストの成果は「バグ件数」だけではない。
**確認した事実と、そこから判断できる品質状態**が成果である。

---

# 6. 「全部テストする」はなぜ不可能か

## 6.1 組み合わせが膨大になる

ソフトウェアには多くの条件が存在する。

例として、ログイン機能だけでも次のような条件がある。

* ユーザーIDが正しい
* パスワードが正しい
* アカウントが有効である
* アカウントがロックされていない
* パスワードの有効期限が切れていない
* 利用者に権限がある
* ブラウザや端末が異なる
* 通信が正常である
* セッションが有効である

これらをすべて組み合わせて確認しようとすると、ケース数はすぐに膨大になる。

## 6.2 入力値も無限に近い

入力項目にも、多くのパターンがある。

例：パスワード入力

* 空欄
* 7文字
* 8文字
* 20文字
* 21文字
* 英字のみ
* 数字のみ
* 記号あり
* 全角文字
* 前後にスペース
* 非常に長い文字列

すべての値を確認することは現実的ではない。
そのため、テストでは**代表的な値やリスクの高い値を選ぶ**必要がある。

## 6.3 時間と人には制約がある

現場では、テストに使える時間や人員は限られている。

そのため、テスト設計では次の判断が必要になる。

* 何を重点的に確認するか
* 何を簡易確認にするか
* 何を今回の対象外にするか
* どのリスクを残すか
* 残したリスクを誰にどう伝えるか

テストは「できるだけたくさん確認する活動」ではない。
**限られた時間で、価値の高い確認を選ぶ活動**である。

# 7. テスト担当者に必要な思考

## 7.1 疑う

テスト担当者は、仕様や実装をそのまま信じすぎない。

ただし、疑うとは、開発者や仕様作成者を責めることではない。
次のように問いを立てることである。

* この仕様で利用者は困らないか
* 例外的な操作はどうなるか
* 入力値が想定外だったらどうなるか
* 権限が違うユーザーではどうなるか
* 途中で処理が失敗したらどうなるか
* 仕様に書かれていない条件はないか

テスト担当者に必要なのは、攻撃的な疑いではなく、**静かな違和感を拾う力**である。

## 7.2 分解する

テスト対象をそのまま大きな塊として見ると、確認漏れが起きやすい。

たとえば「ユーザー登録機能」を見る場合、次のように分解できる。

* 入力項目
* 必須チェック
* 文字数チェック
* 形式チェック
* 重複チェック
* 登録処理
* 登録後の画面表示
* 登録後のデータ状態
* メール通知
* 権限
* エラー処理

分解することで、何を確認すべきかが見えやすくなる。

## 7.3 観察する

テストでは、起きたことを正確に観察する必要がある。

悪い記録の例：

```text
エラーになった。
```

良い記録の例：

```text
登録ボタン押下後、「メールアドレスは既に使用されています」というエラーメッセージが表示された。
画面遷移は発生せず、入力値は保持された。
```

観察が曖昧だと、欠陥報告や原因調査が難しくなる。
テスト担当者は、**何が起きたかを具体的に言語化する力**が必要である。

---

# 8. テストタイプ：機能、非機能、回帰

## 8.1 機能テスト

機能テストは、対象が仕様どおりの機能を提供しているかを確認するテストである。

例：

* ユーザー登録できる
* ログインできる
* 検索できる
* 申請できる
* 承認できる
* 帳票を出力できる

## 8.2 非機能テスト

非機能テストは、機能そのもの以外の品質特性を確認するテストである。

例：

* 応答時間は許容範囲か
* 大量データでも処理できるか
* 権限のないユーザーが操作できないか
* エラーメッセージは理解しやすいか
* 障害時に安全に復旧できるか

この講義では詳細には踏み込まないが、テスト観点として非機能も存在することを理解しておく。

## 8.3 回帰テスト

回帰テストは、変更によって既存機能が壊れていないかを確認するテストである。

例：

* 不具合修正後に、修正箇所の周辺機能を確認する
* 共通部品を変更したため、複数画面を確認する
* パスワード仕様変更後に、ログイン、登録、変更、リセットを確認する

回帰テストは「全部やり直すこと」ではない。
どこに影響がありそうかを考えて、範囲を決める必要がある。

---

# 9. テスト観点

## 9.1 テスト観点とは

テスト観点とは、テスト対象を見るときの切り口である。

仕様を読んでいきなりテストケースを書くのではなく、まずは「どのような観点で確認すべきか」を考える。

## 9.2 主なテスト観点

| 観点    | 確認例                  |
| ----- | -------------------- |
| 入力値   | 空欄、最大値、最小値、不正値、形式違反  |
| 出力結果  | 表示内容、計算結果、メッセージ、帳票内容 |
| 状態    | 下書き、申請中、承認済み、取消済み    |
| 権限    | 一般ユーザー、管理者、承認者       |
| 操作順序  | 通常操作、戻る、再読み込み、二重クリック |
| データ更新 | 登録、更新、削除、履歴、関連テーブル   |
| エラー処理 | 入力エラー、通信エラー、権限エラー    |
| 外部連携  | メール送信、API連携、ファイル出力   |
| 回帰影響  | 変更箇所、共通処理、周辺機能       |
| 非機能   | 性能、使いやすさ、セキュリティ、信頼性  |

## 9.3 テスト観点を持つ意味

テスト観点を持つことで、次の効果がある。

* 確認漏れを減らせる
* 仕様を構造的に読める
* テスト条件を整理しやすくなる
* レビューしやすくなる
* テスト設計の意図を説明しやすくなる

---

# 10. トレーサビリティ

## 10.1 トレーサビリティとは

トレーサビリティとは、仕様、テスト条件、テストケース、実行結果、欠陥をつなげて追跡できるようにすることである。

```text
仕様項目
  ↓
テスト条件
  ↓
テストケース
  ↓
実行結果
  ↓
欠陥報告
```

## 10.2 なぜ必要か

トレーサビリティがないと、次のような問題が起きる。

* どの仕様を確認したのかわからない
* どのテストケースがどの仕様に対応しているかわからない
* 仕様変更時に、どのテストを修正すべきかわからない
* 不具合がどの要件に関係するかわからない
* テスト漏れを説明できない

テストは、実行結果だけでなく、**何に基づいて何を確認したのか**が重要である。

---

# 11. 仕様項目とテスト条件の違い

## 11.1 仕様項目とは

仕様項目とは、仕様書や要件に書かれている内容である。

例：

```text
パスワードは8文字以上20文字以下で入力できる。
```

## 11.2 テスト条件とは

テスト条件とは、その仕様を確認するために見るべき条件である。

上記の仕様からは、たとえば次のようなテスト条件を抽出できる。

| テスト条件             | 意図      |
| ----------------- | ------- |
| 7文字のパスワードはエラーになる  | 下限未満の確認 |
| 8文字のパスワードは登録できる   | 下限値の確認  |
| 20文字のパスワードは登録できる  | 上限値の確認  |
| 21文字のパスワードはエラーになる | 上限超過の確認 |
| 空欄の場合はエラーになる      | 必須入力の確認 |

## 11.3 仕様項目とテスト条件の違い

| 種別     | 内容                |
| ------ | ----------------- |
| 仕様項目   | システムが満たすべき内容      |
| テスト条件  | その仕様を確認するための観点・条件 |
| テストケース | 実行できる具体的な手順と期待結果  |

流れとしては、次のように考える。

```text
仕様項目
  ↓
テスト観点
  ↓
テスト条件
  ↓
テストケース
```

仕様からいきなりテストケースを書くと、確認漏れや重複が起きやすい。
まずテスト条件を整理することで、テスト設計の見通しが良くなる。

# 12. ミニワーク

## 12.1 題材

次の仕様を読み、テスト観点とテスト条件を考える。

```text
ユーザーはメールアドレスとパスワードを入力してログインできる。
パスワードは8文字以上20文字以下とする。
ログインに5回失敗した場合、アカウントをロックする。
ロックされたアカウントではログインできない。
```

## 12.2 作業内容

次の3つを記入する。

| 作業    | 内容             |
| ----- | -------------- |
| テスト観点 | どのような切り口で確認するか |
| テスト条件 | 何を確認すべきか       |
| 不明点   | 仕様として確認したいこと   |

## 12.3 回答例

### テスト観点

| 観点    | 内容                 |
| ----- | ------------------ |
| 入力値   | メールアドレス、パスワードの入力内容 |
| 認証    | 正しい認証情報でログインできるか   |
| エラー処理 | 誤った情報でエラーになるか      |
| ロック   | 5回失敗時にロックされるか      |
| 状態    | ロック済みアカウントの扱い      |
| 表示    | エラーメッセージやロック通知     |
| 回帰    | パスワード仕様変更時の周辺影響    |

### テスト条件

| No | テスト条件                          |
| -: | ------------------------------ |
|  1 | 正しいメールアドレスと正しいパスワードでログインできる    |
|  2 | 存在しないメールアドレスではログインできない         |
|  3 | 正しいメールアドレスと誤ったパスワードではログインできない  |
|  4 | パスワードが7文字の場合はエラーになる            |
|  5 | パスワードが8文字の場合は入力条件を満たす          |
|  6 | パスワードが20文字の場合は入力条件を満たす         |
|  7 | パスワードが21文字の場合はエラーになる           |
|  8 | ログイン失敗が4回まではロックされない            |
|  9 | ログイン失敗が5回に達したらロックされる           |
| 10 | ロック済みアカウントでは正しいパスワードでもログインできない |

### 不明点

| No | 不明点                                |
| -: | ---------------------------------- |
|  1 | ロック後、解除方法はあるか                      |
|  2 | 失敗回数はいつリセットされるか                    |
|  3 | メールアドレスの形式チェックはあるか                 |
|  4 | ログイン失敗時のエラーメッセージは、ID誤りとパスワード誤りで同じか |
|  5 | ロック状態は管理者画面などで確認できるか               |
|  6 | ロック時に通知メールは送信されるか                  |

# 13. まとめ

第1回では、テスト設計の前提となる考え方を扱った。

重要なポイントは次のとおり。

* テストは、品質に関する判断材料を集める活動である
* すべてをテストすることはできない
* テスト担当者には、疑う、分解する、観察する思考が必要である
* テストには、機能、非機能、回帰など複数のタイプがある
* テスト観点を持つことで、確認漏れを減らせる
* 仕様項目とテスト条件は異なる
* テストケースを書く前に、まず何を確認すべきかを整理する
