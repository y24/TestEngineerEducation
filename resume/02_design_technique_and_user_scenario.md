# 第2回 レジュメ

## テスト設計技法とシナリオテスト設計

## 1. 講義の位置づけ

第1回では、ソフトウェアテストの目的、全部テストできない理由、テスト観点、仕様項目とテスト条件の違いを扱った。

第2回では、その次の段階として、**抽出したテスト条件をどのようにテストケースへ落とし込むか**を扱う。

ただし、テスト設計は入力値の確認だけではない。
実際の利用者は、単独の項目を確認するためにシステムを使うわけではなく、何らかの目的を達成するためにシステムを使う。

そのため、この回では次の2つを柱にする。

| 柱            | 内容                       |
| ------------ | ------------------------ |
| 条件をケース化する技術  | 同値分割・境界値分析、デシジョンテーブル     |
| 流れをシナリオ化する技術 | ユーザーストーリー抽出、成功・代替・例外シナリオ |

第2回の中心は、**テスト条件を、実行可能なテストケースや業務シナリオに変換すること**である。

# 4. 第1回の復習：テスト条件からテストケースへ

第1回では、仕様からいきなりテストケースを書くのではなく、まずテスト観点とテスト条件を整理することを学んだ。

流れは次のとおりである。

```text
仕様項目
  ↓
テスト観点
  ↓
テスト条件
  ↓
テストケース / シナリオテスト
```

たとえば、次の仕様があるとする。

```text
パスワードは8文字以上20文字以下で入力できる。
```

この仕様から、次のようなテスト条件を抽出できる。

| テスト条件             | 意図      |
| ----------------- | ------- |
| 7文字のパスワードはエラーになる  | 下限未満の確認 |
| 8文字のパスワードは登録できる   | 下限値の確認  |
| 20文字のパスワードは登録できる  | 上限値の確認  |
| 21文字のパスワードはエラーになる | 上限超過の確認 |

第2回では、このようなテスト条件を、実行できる形に変換する。

# 5. テスト条件をケース化するとは

## 5.1 テスト条件とテストケースの違い

テスト条件は、**何を確認するか**を表す。
テストケースは、**どのように確認するか**を表す。

| 種別     | 例                                                     |
| ------ | ----------------------------------------------------- |
| テスト条件  | 7文字のパスワードはエラーになる                                      |
| テストケース | パスワード欄に7文字の値を入力し、登録ボタンを押す。エラーメッセージが表示され、登録されないことを確認する |

つまり、テスト条件は確認対象であり、テストケースは実行手順である。

## 5.2 テストケースに必要な要素

良いテストケースには、最低限次の要素が必要である。

| 要素         | 内容            |
| ---------- | ------------- |
| 前提条件       | 実行前に必要な状態     |
| 入力値・テストデータ | 使用する具体的な値     |
| 操作手順       | 実行する操作        |
| 期待結果       | 本来どうなるべきか     |
| 確認観点       | 何を確認するためのケースか |

たとえば、次のように書く。

| 項目   | 内容                          |
| ---- | --------------------------- |
| 前提条件 | ユーザー登録画面を表示している             |
| 入力値  | パスワードに7文字の値 `abc1234` を入力する |
| 手順   | 必須項目を入力し、登録ボタンを押す           |
| 期待結果 | パスワード文字数エラーが表示され、登録処理は行われない |
| 確認観点 | パスワード下限未満の入力制御              |

ここで重要なのは、**期待結果が観察できる形で書かれていること**である。

「正しく動く」「エラーになる」だけでは足りない。
どの画面に、どのメッセージが表示され、データ状態がどうなるのかまで書けると、テストケースとして使いやすくなる。

# 6. 同値分割・境界値分析：範囲と代表値を考える

## 6.1 この技法を使う場面

同値分割と境界値分析は、入力値や範囲条件を扱うときに使いやすい。

たとえば、次のような仕様である。

* 1文字以上20文字以下
* 0円以上100,000円以下
* 開始日は終了日以前
* 数量は1以上999以下
* 添付ファイルは10MB以下
* パスワードは8文字以上20文字以下

全部の値を試すことはできないため、代表的な値を選ぶ。

## 6.2 同値分割とは

同値分割とは、同じように扱われる値をグループに分ける考え方である。

例：

```text
金額は1円以上100,000円以下で入力できる。
```

この場合、値を次のように分けられる。

| 区分          |       値の範囲 | 種別 |
| ----------- | ---------: | -- |
| 1円未満        |       0円など | 無効 |
| 1円〜100,000円 |  50,000円など | 有効 |
| 100,001円以上  | 100,001円など | 無効 |

このように、すべての値を試すのではなく、同じ意味を持つ範囲から代表値を選ぶ。

## 6.3 境界値分析とは

境界値分析とは、範囲の端に注目する考え方である。

不具合は、範囲の中央よりも境界付近で起きやすい。
たとえば「以下」と「未満」、「以上」と「より大きい」の実装ミスは、境界で見つかることが多い。

例：

```text
金額は1円以上100,000円以下で入力できる。
```

確認値の例は次のとおり。

| 観点    |      確認値 | 期待  |
| ----- | -------: | --- |
| 下限未満  |       0円 | エラー |
| 下限    |       1円 | 入力可 |
| 有効範囲内 |  50,000円 | 入力可 |
| 上限    | 100,000円 | 入力可 |
| 上限超過  | 100,001円 | エラー |

## 6.4 この項のポイント

同値分割・境界値分析では、次の考え方を持つ。

* 全部の値を試すのではなく、代表値を選ぶ
* 有効な値だけでなく、無効な値も確認する
* 範囲の境界付近を重点的に見る
* 仕様の「以上」「以下」「未満」「より大きい」に注意する

この講義では、同値分割と境界値分析を厳密に分けて暗記するより、まずは次のように覚える。

> 範囲がある仕様では、範囲の中・外・境目を見る。

# 7. デシジョンテーブル：条件の組み合わせを整理する

## 7.1 この技法を使う場面

デシジョンテーブルは、複数の条件の組み合わせによって結果が変わる場合に使う。

たとえば、次のような仕様である。

* 会員種別と購入金額によって割引率が変わる
* ユーザー権限と申請状態によって操作可否が変わる
* 入力状態と承認状態によってボタンの表示が変わる
* アカウント状態と認証結果によってログイン可否が変わる

複数条件を頭の中だけで考えると、確認漏れや矛盾が起きやすい。
そのため、表で整理する。

## 7.2 デシジョンテーブルの基本

デシジョンテーブルは、条件と結果を表にしたものである。

例：ログイン判定

```text
ユーザーID、パスワードが正しく、アカウントがロックされていない場合にログインできる。
```

| 条件 / ルール        | R1 | R2 | R3 | R4 |
| --------------- | -: | -: | -: | -: |
| ユーザーIDが正しい      |  Y |  Y |  N |  N |
| パスワードが正しい       |  Y |  N |  Y |  N |
| アカウントがロックされていない |  Y |  Y |  Y |  Y |
| ログイン成功          |  Y |  N |  N |  N |
| エラー表示           |  N |  Y |  Y |  Y |

さらに、ロック済みの場合も含めると次のようになる。

| 条件 / ルール        | R1 | R2 | R3 | R4 | R5 |
| --------------- | -: | -: | -: | -: | -: |
| ユーザーIDが正しい      |  Y |  Y |  Y |  N |  - |
| パスワードが正しい       |  Y |  Y |  N |  - |  - |
| アカウントがロックされていない |  Y |  N |  Y |  Y |  N |
| ログイン成功          |  Y |  N |  N |  N |  N |
| ロックエラー          |  N |  Y |  N |  N |  Y |
| 認証エラー           |  N |  N |  Y |  Y |  N |

`-` は、その条件が結果に影響しない、または確認しなくてよいことを表す。

## 7.3 デシジョンテーブルの利点

デシジョンテーブルには、次の利点がある。

* 条件の組み合わせ漏れに気づきやすい
* 仕様の矛盾に気づきやすい
* 期待結果を整理しやすい
* レビューしやすい
* テストケース化しやすい

特に業務システムでは、権限、状態、金額、区分、承認状況など、複数条件が絡むことが多い。
そのため、デシジョンテーブルは実務で使いやすい技法である。

## 7.4 この項のポイント

デシジョンテーブルでは、次の考え方を持つ。

* 条件が複数ある場合は表で整理する
* すべての組み合わせが必要とは限らない
* 結果が同じ組み合わせはまとめられることがある
* 表にすることで、仕様の抜けや矛盾が見えやすくなる

条件が増えると、頭の中のメモリはすぐ満杯になる。
人間の脳は意外と根性論に弱い。表に逃がした方がいい。

# 8. シナリオテスト設計：ユーザーストーリーから流れを考える

## 8.1 シナリオテストとは

シナリオテストとは、利用者が目的を達成するまでの一連の流れを確認するテストである。

単発のテストケースとの違いは、次のように整理できる。

| 種別        | 見るもの          | 例                     |
| --------- | ------------- | --------------------- |
| 単発のテストケース | 個別条件や個別機能     | 金額100,001円でエラーになる     |
| シナリオテスト   | 利用者の目的達成までの流れ | 経費申請を作成し、上長に申請し、承認される |

単発のテストケースは、条件を細かく確認するのに向いている。
シナリオテストは、機能同士のつながりや業務の流れを確認するのに向いている。

## 8.2 なぜシナリオテストが必要か

個別機能が正しく動いていても、利用者の目的が達成できないことがある。

例：

* 申請はできるが、承認者の一覧に表示されない
* 登録はできるが、登録後の検索で見つからない
* 下書き保存はできるが、再編集できない
* 承認はできるが、承認後のステータスが更新されない
* 帳票は出力できるが、後続業務で必要な項目が不足している

このような問題は、単一画面だけを見ていると見落としやすい。

シナリオテストでは、**利用者の目的、業務の流れ、状態変化、後続影響**を確認する。

## 8.3 ユーザーストーリーとは

ユーザーストーリーは、利用者が何をしたいのかを表す短い記述である。

基本形は次のとおり。

```text
＜利用者＞として、
＜目的＞したい。
それは＜価値＞のためである。
```

例：

```text
申請者として、
経費申請を提出したい。
それは、承認後に精算してもらうためである。
```

```text
承認者として、
提出された経費申請を確認し、承認または差戻ししたい。
それは、誤った支払いを防ぐためである。
```

```text
管理者として、
ユーザーの権限を変更したい。
それは、担当業務に応じた操作範囲を設定するためである。
```

ユーザーストーリーを考えることで、システムを「画面や項目の集合」ではなく、**利用者の目的を支えるもの**として見られるようになる。

## 8.4 ユーザーストーリーからシナリオへ展開する

ユーザーストーリーから、次のようにシナリオを展開する。

```text
ユーザー
  ↓
目的
  ↓
開始条件
  ↓
操作の流れ
  ↓
終了条件
  ↓
成功・代替・例外シナリオ
```

例：

```text
申請者として、
経費申請を提出したい。
それは、承認後に精算してもらうためである。
```

このユーザーストーリーから、次のシナリオを考えられる。

| 種別     | シナリオ                  |
| ------ | --------------------- |
| 成功シナリオ | 必須項目を入力し、経費申請を提出する    |
| 代替シナリオ | 途中で下書き保存し、後で再編集して提出する |
| 代替シナリオ | 添付ファイルなしで申請する         |
| 例外シナリオ | 必須項目未入力で申請しようとする      |
| 例外シナリオ | 金額上限を超えて申請しようとする      |
| 例外シナリオ | 申請後に編集しようとする          |
| 例外シナリオ | 権限のないユーザーが申請しようとする    |

## 8.5 成功シナリオ、代替シナリオ、例外シナリオ

シナリオは、正常な流れだけではない。

| 種別     | 内容                  |
| ------ | ------------------- |
| 成功シナリオ | 利用者が通常どおり目的を達成する流れ  |
| 代替シナリオ | 通常とは異なるが、許容される流れ    |
| 例外シナリオ | エラー、中断、失敗、不正操作などの流れ |

例：経費申請

| 種別     | 例                         |
| ------ | ------------------------- |
| 成功シナリオ | 必須項目を入力して申請し、承認者の一覧に表示される |
| 代替シナリオ | 下書き保存し、後で再編集して申請する        |
| 例外シナリオ | 金額上限を超えて申請し、エラーになる        |
| 例外シナリオ | 差戻し後に修正して再申請する            |
| 例外シナリオ | 承認済みの申請を編集しようとして拒否される     |

正常系だけを確認しても、利用者が実際に遭遇する問題は見つけきれない。
失敗、寄り道、やり直し、中断、権限違いもシナリオとして考える。

## 8.6 シナリオ抽出の観点

シナリオを考えるときは、次の観点を使う。

| 観点   | 問い               |
| ---- | ---------------- |
| 利用者  | 誰が使うのか           |
| 目的   | 何を達成したいのか        |
| 開始条件 | どの状態から始まるのか      |
| 終了条件 | 何ができたら成功なのか      |
| 主経路  | 通常はどのような流れか      |
| 代替経路 | 別の進み方はあるか        |
| 例外経路 | 失敗、中断、エラーはあるか    |
| 状態変化 | データやステータスはどう変わるか |
| 権限   | 誰ならできて、誰ならできないか  |
| 後続影響 | 次の業務や機能に影響するか    |

この観点を使うと、単なる操作確認から一段上がる。
特に「終了条件」「状態変化」「後続影響」は大事である。

## 8.7 シナリオテスト設計の成果物例

シナリオは、次のような表で整理できる。

| ID        | ユーザーストーリー        | シナリオ           | 種別 | 確認したいこと             |
| --------- | ---------------- | -------------- | -- | ------------------- |
| US-01-S01 | 申請者として経費申請を提出したい | 必須項目を入力して申請する  | 成功 | 申請が提出され、状態が「申請中」になる |
| US-01-S02 | 同上               | 下書き保存して後で再編集する | 代替 | 下書き状態で保存され、再編集できる   |
| US-01-S03 | 同上               | 必須項目未入力で申請する   | 例外 | エラーが表示され、状態が変わらない   |
| US-01-S04 | 同上               | 金額上限を超えて申請する   | 例外 | 金額エラーが表示され、申請されない   |
| US-01-S05 | 同上               | 申請後に編集しようとする   | 例外 | 編集不可である             |

この表を作ることで、どの利用者のどの目的に対して、どのような流れを確認するのかが見える。

# 9. エラー推測

## 9.1 エラー推測とは

エラー推測とは、過去の経験や対象システムの特徴から、欠陥がありそうな場所を考える技法である。

ただの思いつきではなく、次のような情報をもとに考える。

* 過去に起きた不具合
* 仕様の曖昧な部分
* 複雑な条件分岐
* 例外的な操作
* 利用者が間違えやすい操作
* データの境界
* 外部連携やファイル出力
* 権限や状態の切り替わり

## 9.2 エラー推測の例

よく疑うべき条件には、次のようなものがある。

| 観点  | 例                       |
| --- | ----------------------- |
| 入力  | 空欄、最大文字数、全角半角、前後スペース、記号 |
| 操作  | 二重クリック、戻る、再読み込み、途中離脱    |
| 状態  | 削除済み、ロック済み、承認済み、期限切れ    |
| 権限  | 権限不足、権限変更直後、別ユーザーのデータ   |
| データ | 重複、存在しないコード、古いデータ、大量データ |
| 連携  | メール送信失敗、API失敗、ファイル出力失敗  |

## 9.3 シナリオテストとの組み合わせ

エラー推測は、シナリオテストと組み合わせると使いやすい。

例：経費申請シナリオ

| シナリオ上の場面 | エラー推測            |
| -------- | ---------------- |
| 入力中      | 必須項目を空欄にする       |
| 金額入力     | 上限を超える金額を入力する    |
| 添付       | サイズの大きいファイルを添付する |
| 申請ボタン押下  | 二重クリックする         |
| 申請後      | 戻るボタンで再編集しようとする  |
| 承認前      | 申請者が内容を変更しようとする  |
| 差戻し後     | 修正せずに再申請しようとする   |

エラー推測では、利用者がきれいに操作してくれるとは限らない、という前提で考える。
現実の利用者は、仕様書の読者ではない。わりと自由に動く。

# 10. 探索的テスト

## 10.1 探索的テストとは

探索的テストとは、テストの実行、観察、学習、次のテスト設計を同時に進めるテストである。

ただし、これは「自由に触ること」ではない。

探索的テストでは、目的を決めて、観察し、気づいたことをもとに次の確認を考える。

## 10.2 探索的テストに必要な要素

最低限、次の要素を持たせる。

| 要素    | 内容           |
| ----- | ------------ |
| チャーター | 今回、何を探るか     |
| 操作    | 実際に試したこと     |
| 観察    | 気づいたこと       |
| 仮説    | なぜそうなったと考えるか |
| 記録    | 再現できるように残すこと |

例：

```text
チャーター：
経費申請の作成から提出までの流れで、入力エラーや状態不整合が起きないかを探る。

観察：
金額上限超過では画面上にエラーが出るが、添付ファイル容量超過ではサーバーエラー画面に遷移した。

仮説：
入力値チェックとファイルチェックで、エラー処理の実装方針が異なっている可能性がある。
```

## 10.3 探索的テストの注意点

探索的テストは、未経験者がそのまま行うと、単なる「なんとなく操作」になりやすい。

そのため、次の点を必ず守る。

* 目的を決めてから始める
* 試したことを記録する
* 気づいたことを残す
* 不具合らしきものは再現手順を確認する
* 次に何を確認するかを考えながら進める

探索的テストは、雑にやるテストではない。
むしろ、観察力と言語化力がかなり要求される。

# 11. 良いテストケースと悪いテストケース

## 11.1 悪いテストケースの例

次のようなテストケースは、実行者によって判断がぶれやすい。

| 項目   | 内容            |
| ---- | ------------- |
| 手順   | 正しい値を入力して登録する |
| 期待結果 | 正常に登録される      |

このケースには、次の問題がある。

* 正しい値が何か不明
* 前提条件が不明
* どの画面で操作するのか不明
* 期待結果が曖昧
* 何を確認するためのケースか不明
* データが登録されたことをどこで確認するのか不明

## 11.2 良いテストケースの例

同じ内容でも、次のように書くと確認しやすくなる。

| 項目   | 内容                                                    |
| ---- | ----------------------------------------------------- |
| 確認観点 | パスワード下限値でユーザー登録できること                                  |
| 前提条件 | ユーザー登録画面を表示している。メールアドレス `test001@example.com` は未登録である |
| 入力値  | メールアドレス：`test001@example.com`、パスワード：`abcd1234`        |
| 手順   | 必須項目を入力し、登録ボタンを押す                                     |
| 期待結果 | 登録完了メッセージが表示される                                       |
| 後続確認 | ユーザー一覧に `test001@example.com` が表示される                  |

このケースでは、実行者が変わっても同じ確認がしやすい。

## 11.3 シナリオテストケースの例

シナリオテストの場合は、単一画面だけでなく、流れと状態変化を見る。

例：経費申請の提出

| 項目   | 内容                                     |
| ---- | -------------------------------------- |
| 確認観点 | 経費申請を提出すると、状態が「申請中」になり、承認者の一覧に表示されること  |
| 前提条件 | 申請者ユーザーでログインしている。承認者が設定済みである           |
| 入力値  | 件名：交通費精算、金額：10,000円、利用日：当月内の日付、支払先：A交通 |
| 手順   | 経費申請画面を開き、必要項目を入力して申請ボタンを押す            |
| 期待結果 | 申請完了メッセージが表示され、申請状態が「申請中」になる           |
| 後続確認 | 承認者ユーザーでログインすると、承認待ち一覧に対象申請が表示される      |

シナリオテストでは、特に次の確認が重要になる。

* 開始状態
* 操作の流れ
* 終了状態
* データの状態変化
* 後続機能への影響
* 別ユーザーから見た結果

## 11.4 良いテストケースの条件

良いテストケースには、次の特徴がある。

* 目的や確認観点が明確である
* 前提条件が明確である
* 入力値が具体的である
* 操作手順が再現できる
* 期待結果が観察可能である
* 後続確認が必要な場合、それが書かれている
* 誰が実行しても同じ判断ができる
* 仕様やテスト条件との対応が追える

テストケースは、実行者への作業指示であると同時に、設計意図を残す文書でもある。

# 12. ミニワーク

## 12.1 題材

次の仕様を読み、ユーザーストーリー、シナリオ、テストケースを考える。

```text
ユーザーは経費申請を作成できる。
申請には、件名、金額、利用日、支払先を入力する。
金額は1円以上100,000円以下とする。
申請者は下書き保存または申請ができる。
申請後、承認者が承認または差戻しできる。
差戻された申請は、申請者が修正して再申請できる。
承認済みの申請は、申請者が編集できない。
```

## 12.2 作業内容

次の内容を考える。

| 作業        | 内容                    |
| --------- | --------------------- |
| ユーザーストーリー | 利用者、目的、価値を整理する        |
| シナリオ      | 成功、代替、例外シナリオを挙げる      |
| 境界値       | 金額の確認値を挙げる            |
| デシジョンテーブル | 操作可否や結果が変わる条件を整理する    |
| テストケース    | 代表シナリオを1件、具体的なケースに落とす |

## 12.3 回答例：ユーザーストーリー

| ID    | ユーザーストーリー                                           |
| ----- | --------------------------------------------------- |
| US-01 | 申請者として、経費申請を提出したい。それは、承認後に精算してもらうためである              |
| US-02 | 承認者として、提出された経費申請を承認または差戻ししたい。それは、申請内容の妥当性を確認するためである |
| US-03 | 申請者として、差戻された申請を修正して再申請したい。それは、誤りを直して承認を受けるためである     |

## 12.4 回答例：シナリオ

| ID   | 種別 | シナリオ                     | 確認したいこと          |
| ---- | -- | ------------------------ | ---------------- |
| S-01 | 成功 | 必須項目を入力し、経費申請を提出する       | 状態が「申請中」になる      |
| S-02 | 代替 | 途中で下書き保存し、後で再編集して申請する    | 下書き保存と再編集ができる    |
| S-03 | 例外 | 金額0円で申請する                | 金額エラーになり申請されない   |
| S-04 | 例外 | 金額100,001円で申請する          | 金額上限エラーになり申請されない |
| S-05 | 成功 | 承認者が申請を承認する              | 状態が「承認済み」になる     |
| S-06 | 例外 | 承認済み申請を申請者が編集しようとする      | 編集できない           |
| S-07 | 代替 | 承認者が申請を差戻し、申請者が修正して再申請する | 差戻し後に再申請できる      |

## 12.5 回答例：境界値

```text
金額は1円以上100,000円以下とする。
```

| 観点    |      確認値 | 期待結果 |
| ----- | -------: | ---- |
| 下限未満  |       0円 | エラー  |
| 下限    |       1円 | 入力可  |
| 有効範囲内 |  50,000円 | 入力可  |
| 上限    | 100,000円 | 入力可  |
| 上限超過  | 100,001円 | エラー  |

# 13. まとめ

第2回では、テスト条件をテストケースやシナリオに落とし込む方法を扱った。

重要なポイントは次のとおり。

* テスト条件は「何を確認するか」、テストケースは「どう確認するか」である
* 同値分割・境界値分析では、範囲の中・外・境目を見る
* デシジョンテーブルでは、複数条件の組み合わせを表で整理する
* シナリオテストでは、利用者の目的達成までの流れを見る
* ユーザーストーリーは、利用者、目的、価値の形で整理する
* シナリオは、成功、代替、例外に分けて考える
* エラー推測では、壊れそうな条件や利用者がやりそうな操作を考える
* 探索的テストは、目的を持って観察し、学びながら確認する活動である
* 良いテストケースは、前提、入力値、手順、期待結果、確認観点が明確である
