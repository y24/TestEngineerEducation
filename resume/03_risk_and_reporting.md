# 第3回 レジュメ

## リスクに基づくテスト判断と報告

## 1. 講義の位置づけ

第1回では、テストの目的、テスト観点、仕様項目とテスト条件の違いを扱った。
第2回では、テスト条件をテストケースやシナリオテストに落とし込む方法を扱った。

第3回では、作成したテストケースやシナリオを前提に、**限られた時間の中で何を優先して確認するか、どこまで確認するか、結果をどう報告するか**を扱う。

テストでは、すべてを同じ厚さで確認することはできない。
そのため、リスクを見て優先順位を付け、必要に応じて「今回はテストしない」という判断も行う必要がある。

また、テストの成果は「実行したこと」だけではない。
関係者がリリース可否や追加対応を判断できるように、欠陥や進捗、残っているリスクを伝えることも重要である。

---

## 2. 到達目標

この回の終了時点で、受講者が次のことを説明・実践できる状態を目指す。

| 到達目標                     | 内容                                  |
| ------------------------ | ----------------------------------- |
| プロダクトリスクとプロジェクトリスクを区別できる | 製品に関するリスクと、テスト活動の進行に関するリスクを分けて考えられる |
| 重要度・発生可能性・優先度を区別できる      | 問題の影響、起きやすさ、対応順を分けて考えられる            |
| テストの優先順位を考えられる           | 限られた時間で、どこを重点的に確認すべきか説明できる          |
| テストしない判断を説明できる           | 対象外にする理由と残存リスクを説明できる                |
| 回帰テスト範囲を考えられる            | 変更箇所、周辺機能、共通部品、過去不具合などから範囲を決められる    |
| 欠陥報告を書ける                 | 再現手順、期待結果、実績結果、証跡を整理して報告できる         |
| テスト進捗を報告できる              | 件数だけでなく、問題・リスク・判断事項を含めて報告できる        |

---

|     時間 | 内容                 |
| -----: | ------------------ |
|   0〜5分 | 第1回・第2回の復習         |
|  5〜15分 | プロダクトリスクとプロジェクトリスク |
| 15〜25分 | 重要度、発生可能性、優先度      |
| 25〜33分 | テストしない判断           |
| 33〜42分 | 回帰テスト範囲の決め方        |
| 42〜52分 | 欠陥報告の書き方           |
| 52〜57分 | テスト進捗報告            |
| 57〜60分 | まとめ                |

# 4. 第1回・第2回の復習

これまでの流れは次のとおりである。

```text
仕様項目
  ↓
テスト観点
  ↓
テスト条件
  ↓
テストケース / シナリオテスト
  ↓
優先順位付け
  ↓
実行・欠陥報告・進捗報告
```

第3回では、下の3つを中心に扱う。

* どのテストを優先するか
* どこまでテストするか
* 結果をどう伝えるか

テスト設計では、確認項目をたくさん出すことも大事だが、それだけでは十分ではない。
現場では時間、人員、環境、リリース日程に制約がある。

そのため、テスト担当者には、**確認すべきことを出す力**だけでなく、**確認の優先順位を考える力**も必要になる。

---

# 5. プロダクトリスクとプロジェクトリスク

## 5.1 リスクとは

リスクとは、将来起こる可能性があり、起きた場合に悪い影響を与えるものを指す。

テストでは、主に次の2種類のリスクを考える。

| 種別        | 内容                  |
| --------- | ------------------- |
| プロダクトリスク  | 製品やシステムそのものに関するリスク  |
| プロジェクトリスク | 開発やテスト活動の進め方に関するリスク |

---

## 5.2 プロダクトリスク

プロダクトリスクは、製品が利用者や業務に悪影響を与えるリスクである。

例：

| リスク             | 影響                 |
| --------------- | ------------------ |
| 金額計算が誤る         | 誤請求、誤精算、会計不整合が発生する |
| 権限のないユーザーが操作できる | 情報漏えい、不正操作につながる    |
| 申請状態が正しく更新されない  | 後続業務が止まる           |
| 帳票に誤った値が出力される   | 顧客・監査・業務判断に影響する    |
| データが保存されない      | 利用者の作業が失われる        |

テスト設計で特に重視するのは、このプロダクトリスクである。

なぜなら、テストは最終的に、製品の利用者や業務への悪影響を減らすために行うからである。

---

## 5.3 プロジェクトリスク

プロジェクトリスクは、テスト活動や開発活動がうまく進まないリスクである。

例：

| リスク               | 影響                   |
| ----------------- | -------------------- |
| 仕様が未確定            | テスト設計がやり直しになる        |
| テスト環境が不安定         | 実行が進まない、結果が信用できない    |
| テストデータが不足している     | 必要な条件を確認できない         |
| 担当者のスキルが不足している    | 欠陥の見落としや報告品質の低下につながる |
| 開発遅延によりテスト期間が短くなる | 確認範囲を削る必要が出る         |

プロジェクトリスクは、テスト設計そのものだけでなく、進捗報告や完了判断に影響する。

たとえば、テストケースが100件あっても、環境不安定で30件が実行できていないなら、品質判断に使える情報は不足している。

---

## 5.4 この項のポイント

新人には、まず次のように理解してもらうとよい。

| 種別        | 簡単な言い方                  |
| --------- | ----------------------- |
| プロダクトリスク  | 製品が壊れて利用者や業務に悪影響を与えるリスク |
| プロジェクトリスク | テスト活動や開発活動がうまく進まないリスク   |

テスト担当者は、プロダクトリスクを見てテストの厚みを考え、プロジェクトリスクを見て進め方や報告内容を考える。

---

# 6. 重要度、発生可能性、優先度

## 6.1 3つの違い

リスクを考えるとき、次の3つを混同しないことが重要である。

| 用語      | 意味                |
| ------- | ----------------- |
| 重要度・影響度 | 問題が起きたときのダメージの大きさ |
| 発生可能性   | 問題が起きそうな度合い       |
| 優先度     | 今どれを先に確認・対応すべきか   |

たとえば、金額計算の誤りは影響度が高い。
一方で、仕様変更が小さく、過去にも不具合が少ない場合、発生可能性は低いかもしれない。

逆に、表示崩れは影響度が低い場合が多いが、画面部品を大きく変更した直後なら発生可能性は高いかもしれない。

---

## 6.2 重要度・影響度

重要度・影響度は、問題が起きたときにどれだけ困るかで考える。

影響度が高い例：

* 金額や数量の誤計算
* データ破壊
* 情報漏えい
* 権限不備
* 業務停止
* リリース後に回復が難しい不具合
* 顧客や監査に影響する誤表示

影響度が低い例：

* 軽微な文言の違い
* 表示位置の小さなずれ
* 利用頻度が低く、業務影響も小さい機能の軽微な問題

ただし、影響度はシステムの性質によって変わる。
たとえば、会計・業務系システムでは、数値、帳票、状態、権限の影響度は高くなりやすい。

---

## 6.3 発生可能性

発生可能性は、その問題が起きそうかどうかで考える。

発生可能性が高い例：

* 変更量が大きい
* 仕様が複雑
* 条件分岐が多い
* 過去に不具合が多い
* 担当者が不慣れ
* 共通部品を変更している
* 外部連携や非同期処理がある
* 手作業の設定やデータ移行がある

発生可能性が低い例：

* 変更がない
* 単純な表示変更のみ
* 過去に安定している
* 既存の共通部品をそのまま利用している

ただし、「変更がないから絶対安全」とは言えない。
共通部品、設定、データ、環境の影響を受けることがある。

---

## 6.4 優先度

優先度は、影響度と発生可能性を踏まえて、今どれを先に扱うべきかを決めるものである。

例：

| 対象      | 影響度 | 発生可能性 | 優先度 | 理由                    |
| ------- | --: | ----: | --: | --------------------- |
| 金額計算    |   高 |     中 |   高 | 誤りが業務に大きく影響する         |
| 権限チェック  |   高 |     中 |   高 | 情報漏えいや不正操作につながる       |
| 申請状態更新  |   高 |     中 |   高 | 後続業務が止まる              |
| 表示文言    |   低 |     中 |   低 | 業務影響が小さい              |
| 画面レイアウト |   中 |     高 |   中 | 操作性に影響するが、業務停止まではしにくい |

優先度は、単純に「影響度が高いもの」だけで決まるわけではない。
発生可能性、利用頻度、検出しやすさ、修正難易度、リリース判断への影響も関係する。

---

## 6.5 リスク評価の簡易表

新人向けには、まず3段階で十分である。

| 影響度 | 発生可能性 | 優先度の考え方          |
| --- | ----- | ---------------- |
| 高   | 高     | 最優先で確認する         |
| 高   | 中     | 重点的に確認する         |
| 高   | 低     | 代表ケースや重要ケースを確認する |
| 中   | 高     | 変更箇所・周辺を確認する     |
| 中   | 中     | 通常の確認対象          |
| 低   | 低     | 簡易確認、または対象外候補    |

この表は絶対的な正解ではない。
あくまで、優先順位を話し合うための道具である。

---

# 7. テストしない判断

## 7.1 テストしない判断とは

テストでは、すべてを確認できない。
そのため、現場では「今回は確認しない」「代表ケースだけにする」「別フェーズで確認する」という判断が必要になる。

ここで重要なのは、**テストしないこと自体が悪いのではなく、理由なく見落とすことが悪い**という点である。

---

## 7.2 テストしない判断に必要な情報

テストしない判断をする場合は、最低限次の情報を整理する。

| 項目    | 内容              |
| ----- | --------------- |
| 対象    | 何をテストしないのか      |
| 理由    | なぜ今回確認しないのか     |
| 影響    | 問題があった場合に何が起きるか |
| 代替策   | 他の確認方法があるか      |
| 残存リスク | 何が未確認として残るか     |
| 判断者   | 誰が了承したか         |

「なんとなく時間がないからやらない」では、テスト判断として弱い。
対象外にするなら、その理由と残るリスクを説明する必要がある。

---

## 7.3 テストしない判断の例

| 対象             | 判断      | 理由                  | 残存リスク              |
| -------------- | ------- | ------------------- | ------------------ |
| 変更されていないヘルプ画面  | 対象外     | 今回の修正影響がないため        | 既存不具合は検出できない       |
| 管理者向け低頻度機能     | 代表ケースのみ | 利用頻度が低く、変更影響も限定的なため | 例外条件の不具合が残る可能性     |
| 外部サービス障害時の詳細挙動 | 対象外     | 検証環境で再現が困難なため       | 障害時のエラー表示に問題が残る可能性 |
| 古いブラウザ         | 対象外     | サポート対象外のため          | 利用された場合の動作は保証しない   |

このように、対象外にする場合でも、残存リスクを明示する。

---

## 7.4 テストしない判断の注意点

テストしない判断では、次の点に注意する。

* 影響度が高いものを安易に対象外にしない
* 「変更していない」は十分な理由とは限らない
* 共通部品や設定変更の影響を確認する
* 対象外にした範囲を記録する
* 必要に応じてリーダーや関係者に判断を仰ぐ

テスト担当者がすべてを決める必要はない。
ただし、判断に必要な情報を整理して出すことは、テスト担当者の重要な役割である。

---

# 8. 回帰テスト範囲の決め方

## 8.1 回帰テストとは

回帰テストとは、変更によって既存機能が壊れていないかを確認するテストである。

不具合修正や機能追加を行うと、その変更箇所だけでなく、周辺機能や共通処理に影響が出ることがある。

回帰テストは、単に「全部やり直すこと」ではない。
変更の影響を考え、必要な範囲を決める活動である。

---

## 8.2 回帰範囲を考える観点

回帰テスト範囲は、次の観点で考える。

| 観点      | 確認すること                   |
| ------- | ------------------------ |
| 変更箇所    | 直接修正された機能                |
| 周辺機能    | 変更箇所とつながる機能              |
| 共通部品    | 共通処理、共通画面、共通API、共通ライブラリ  |
| 同じデータ   | 同じテーブル、同じマスタ、同じファイルを使う機能 |
| 同じ業務フロー | 前後の業務や後続処理               |
| 権限・状態   | 状態遷移や権限制御に関係する機能         |
| 過去不具合   | 過去に不具合が多かった箇所            |
| 重要機能    | 業務影響が大きい機能               |

---

## 8.3 回帰テスト範囲の例

例：

```text
パスワードポリシーを変更し、最小文字数を8文字から12文字に変更した。
```

この場合、変更箇所だけを考えると「パスワード入力欄」だけに見える。

しかし、実際には次のような範囲が影響を受ける可能性がある。

| 範囲              | 理由                       |
| --------------- | ------------------------ |
| ユーザー登録          | 新規登録時にパスワードを入力するため       |
| ログイン            | 既存ユーザーのログインに影響する可能性があるため |
| パスワード変更         | 新しいポリシーが適用されるため          |
| パスワードリセット       | 再設定時にポリシーが適用されるため        |
| 管理者による初期パスワード発行 | 管理者機能で同じ制約を使う可能性があるため    |
| アカウントロック        | 認証失敗と関係するため              |
| エラーメッセージ        | 表示文言が変わる可能性があるため         |
| API             | 画面以外からパスワード設定できる場合があるため  |

修正は小さく見えても、影響範囲は意外と広い。
小さな石を池に落としたときの波紋みたいなものだね。コードの池は、たまに濁っているけど。

---

## 8.4 回帰テスト範囲の決め方

回帰範囲は、次の流れで決めるとよい。

```text
1. 何が変更されたかを確認する
2. 変更箇所が使っている部品・データ・設定を確認する
3. 周辺機能や後続業務への影響を考える
4. 影響度と発生可能性を見て優先順位を付ける
5. 確認する範囲、簡易確認にする範囲、対象外にする範囲を決める
6. 対象外や未確認のリスクを報告する
```

---

## 8.5 回帰テスト範囲の記録例

| 対象        | 確認レベル | 理由                |
| --------- | ----- | ----------------- |
| パスワード変更   | 重点確認  | 直接変更箇所であるため       |
| ユーザー登録    | 重点確認  | 同じ入力制約を使うため       |
| パスワードリセット | 重点確認  | 同じポリシー適用が必要なため    |
| ログイン      | 代表確認  | 既存認証への影響確認のため     |
| 管理者機能     | 簡易確認  | 初期パスワード発行に影響する可能性 |
| プロフィール編集  | 対象外   | パスワード項目を扱わないため    |

---

# 9. 欠陥報告の書き方

## 9.1 欠陥報告の目的

欠陥報告は、開発者を責めるための文書ではない。
発生した問題を、再現・調査・修正・判断できるように伝えるための文書である。

良い欠陥報告は、次の役に立つ。

* 開発者が再現できる
* 原因調査がしやすい
* 修正の優先度を判断できる
* 影響範囲を考えやすい
* テスト担当者や関係者が状況を共有できる

---

## 9.2 欠陥報告に必要な項目

| 項目   | 内容                     |
| ---- | ---------------------- |
| タイトル | 何が起きたか一目でわかる           |
| 発生環境 | OS、ブラウザ、バージョン、テスト環境など  |
| 前提条件 | データ状態、ログインユーザー、権限など    |
| 再現手順 | 同じ事象を再現できる操作           |
| 期待結果 | 本来どうなるべきか              |
| 実績結果 | 実際に何が起きたか              |
| 再現率  | 毎回起きるのか、ときどき起きるのか      |
| 影響範囲 | 業務や利用者への影響             |
| 証跡   | 画面キャプチャ、ログ、動画、出力ファイルなど |
| 補足   | 関連チケット、類似不具合、発生条件など    |

すべてを長く書く必要はない。
ただし、再現に必要な情報と、判断に必要な情報は省略しない。

---

## 9.3 タイトルの書き方

悪いタイトル：

```text
エラーになる
```

```text
登録できない
```

良いタイトル：

```text
ユーザー登録で8文字のパスワードを入力すると、文字数エラーとなり登録できない
```

```text
承認済みの経費申請を戻るボタン経由で編集できてしまう
```

タイトルは、何が、どの条件で、どうなるのかがわかるように書く。

---

## 9.4 再現手順

再現手順は、別の人が同じ事象を再現できるように書く。

悪い例：

```text
経費申請を登録するとエラーになります。
```

良い例：

```text
1. 申請者ユーザーでログインする
2. 経費申請画面を開く
3. 件名に「交通費精算」を入力する
4. 金額に「100000」を入力する
5. 利用日に当月の日付を入力する
6. 支払先に「A交通」を入力する
7. 申請ボタンを押す
```

再現手順は、操作の地図である。
地図が雑だと、調査する人は迷子になる。しかもだいたい忙しい時間に迷子になる。

---

## 9.5 期待結果と実績結果

欠陥報告では、期待結果と実績結果を分けて書く。

悪い例：

```text
エラーになります。
```

良い例：

```text
期待結果：
金額100,000円は上限値として許可されるため、経費申請が提出される。

実績結果：
「金額は1円以上100,000円以下で入力してください」というエラーメッセージが表示され、申請できない。
```

期待結果が書けない場合、仕様理解が曖昧な可能性がある。
その場合は、欠陥として起票する前に、仕様確認が必要なこともある。

---

## 9.6 実績結果の書き方

実績結果は、観察した事実を書く。

悪い例：

```text
たぶんバリデーションがおかしいです。
```

良い例：

```text
申請ボタン押下後、画面上部に「金額は1円以上100,000円以下で入力してください」と表示される。
申請一覧に対象データは追加されていない。
ブラウザの開発者ツールでは、申請APIが呼び出されていない。
```

原因の推測を書く場合は、事実と分けて書く。

```text
補足：
上限値100,000円を超過として扱っている可能性がある。
```

## 9.7 重大度と優先度

欠陥報告では、重大度と優先度も混同しやすい。

| 用語  | 意味                 |
| --- | ------------------ |
| 重大度 | 欠陥が製品や業務に与える影響の大きさ |
| 優先度 | どの順番で対応すべきか        |

例：

| 欠陥                 | 重大度 | 優先度 | 理由                        |
| ------------------ | --: | --: | ------------------------- |
| 金額計算が誤る            |   高 |   高 | 業務影響が大きく、早急な修正が必要         |
| 管理画面の文言誤り          |   低 |   低 | 影響が小さい                    |
| ログイン画面の会社ロゴが表示されない |   低 |   高 | リリース直前の見た目品質として優先される場合がある |
| 低頻度機能で500エラー       |   中 | 低〜中 | 利用頻度や回避策による               |

重大度は影響の大きさ。
優先度は対応順。
この2つは似ているけど、同じではない。

# 10. テスト進捗報告

## 10.1 テスト進捗報告の目的

テスト進捗報告の目的は、「どれだけ頑張ったか」を伝えることではない。
関係者が現在の状況を理解し、必要な判断をできるようにすることである。

進捗報告では、件数だけでなく、次の情報を伝える必要がある。

* どこまで終わったか
* 結果はどうだったか
* 重大な問題はあるか
* 未実行や保留はあるか
* テストを妨げている問題はあるか
* リリース判断に影響するリスクはあるか

---

## 10.2 最低限報告すべき項目

| 項目      | 内容                  |
| ------- | ------------------- |
| 実行状況    | 計画件数、実行済み件数、未実行件数   |
| 結果      | OK、NG、保留、ブロック       |
| 欠陥状況    | 新規欠陥、未解決欠陥、重大欠陥     |
| 遅延・阻害要因 | 環境不具合、仕様未確定、データ不足など |
| 残存リスク   | 未確認範囲、重大欠陥、対象外範囲    |
| 判断事項    | 続行、延期、範囲変更、追加確認など   |

---

## 10.3 悪い進捗報告と良い進捗報告

悪い報告：

```text
テストは70%終わりました。
不具合がいくつかあります。
```

これでは、状況判断が難しい。

良い報告：

```text
予定100件中70件を実行済み。
結果はOK 58件、NG 8件、保留4件、未実行30件。

NG 8件のうち、重大度高の欠陥が2件あります。
2件はいずれも金額計算に関係しており、リリース判断に影響します。

未実行30件のうち10件は、テスト環境のデータ不備によりブロックされています。
残り20件は予定どおり明日実行予定です。

現時点では、金額計算まわりの重大欠陥が解消されるまで、完了判断は難しい状態です。
```

このように、進捗、品質、阻害要因、判断事項を分けて伝える。

# 11. ミニワーク

## 11.1 題材

次の変更内容を読み、リスク、回帰範囲、欠陥報告、進捗報告を考える。

```text
パスワードポリシー変更により、パスワードの最小文字数を8文字から12文字に変更した。
対象はユーザー登録、パスワード変更、パスワードリセットである。
ただし、リリースまでの時間が短く、すべての関連機能を詳細に確認する時間はない。
```

---

## 11.2 作業内容

次の内容を考える。

| 作業       | 内容                |
| -------- | ----------------- |
| リスク      | どのような問題が起きると困るか   |
| 優先度      | 何を重点的に確認するか       |
| 回帰範囲     | どの機能を確認するか        |
| テストしない範囲 | 今回対象外にする範囲と理由     |
| 欠陥報告     | 不具合を1件想定し、報告内容を書く |
| 進捗報告     | テスト途中の状況を報告する     |

---

## 11.3 回答例：リスクと優先度

| 対象        | リスク                   | 影響度 | 発生可能性 | 優先度 |
| --------- | --------------------- | --: | ----: | --: |
| ユーザー登録    | 12文字未満のパスワードで登録できてしまう |   高 |     中 |   高 |
| パスワード変更   | 12文字以上でもエラーになる        |   高 |     中 |   高 |
| パスワードリセット | 新ポリシーが適用されない          |   高 |     中 |   高 |
| ログイン      | 既存ユーザーがログインできなくなる     |   高 |     低 |   中 |
| エラーメッセージ  | 旧仕様の「8文字以上」と表示される     |   中 |     中 |   中 |
| 管理者機能     | 初期パスワード発行に旧仕様が残る      |   中 |     低 |   中 |

---

## 11.4 回答例：回帰テスト範囲

| 対象              | 確認レベル | 理由              |
| --------------- | ----- | --------------- |
| ユーザー登録          | 重点確認  | 直接対象機能であるため     |
| パスワード変更         | 重点確認  | 直接対象機能であるため     |
| パスワードリセット       | 重点確認  | 直接対象機能であるため     |
| ログイン            | 代表確認  | 既存ユーザーへの影響確認のため |
| エラーメッセージ        | 代表確認  | 利用者案内に影響するため    |
| 管理者による初期パスワード発行 | 簡易確認  | 関連機能である可能性があるため |
| プロフィール編集        | 対象外   | パスワードを扱わないため    |

---

## 11.5 回答例：テストしない範囲

| 対象           | 判断     | 理由               | 残存リスク             |
| ------------ | ------ | ---------------- | ----------------- |
| サポート対象外ブラウザ  | 対象外    | 対応範囲外のため         | 対象外環境での動作は未確認     |
| プロフィール編集     | 対象外    | パスワード項目を扱わないため   | 間接影響があった場合は検出できない |
| 管理者機能の詳細パターン | 簡易確認のみ | 利用頻度と時間制約を踏まえたため | 例外条件の不具合が残る可能性    |

---

## 11.6 回答例：欠陥報告

```text
タイトル：
ユーザー登録で12文字のパスワードを入力しても、文字数エラーとなり登録できない

発生環境：
- テスト環境：ST環境
- バージョン：v1.2.3
- ブラウザ：Chrome
- ユーザー：未ログイン状態

前提条件：
- ユーザー登録画面を表示している
- メールアドレス test001@example.com は未登録である

再現手順：
1. ユーザー登録画面を開く
2. メールアドレスに test001@example.com を入力する
3. パスワードに abcdef123456 を入力する
4. その他必須項目を入力する
5. 登録ボタンを押す

期待結果：
- パスワードは12文字で新しい最小文字数を満たしているため、ユーザー登録が完了する

実績結果：
- 「パスワードは8文字以上20文字以下で入力してください」というエラーメッセージが表示され、登録できない

再現率：
- 3回中3回発生

影響：
- 新規ユーザーが登録できない可能性があり、リリース判断に影響する

証跡：
- 画面キャプチャあり
```

## 11.7 回答例：進捗報告

```text
パスワードポリシー変更に関するテスト進捗です。

計画20件中、14件を実行済みです。
結果はOK 10件、NG 3件、保留1件、未実行6件です。

NG 3件のうち、重大度高が1件あります。
内容は、ユーザー登録で12文字のパスワードを入力しても登録できない問題です。
新規ユーザー登録に影響するため、リリース判断に関係します。

未実行6件のうち、2件はパスワードリセットメールが送信されない環境不具合によりブロックされています。
残り4件は本日中に実行予定です。

現時点では、ユーザー登録の重大欠陥が解消されるまで、パスワードポリシー変更部分の完了判断は難しい状態です。
```

# 12. まとめ

第3回では、テスト設計後の優先順位付け、回帰範囲、欠陥報告、進捗報告を扱った。

重要なポイントは次のとおり。

* プロダクトリスクは、製品や業務に悪影響を与えるリスクである
* プロジェクトリスクは、テスト活動や開発活動がうまく進まないリスクである
* 重要度・影響度、発生可能性、優先度は分けて考える
* テストでは、すべてを同じ厚さで確認することはできない
* テストしない判断には、理由と残存リスクの説明が必要である
* 回帰テストは、変更箇所だけでなく、周辺機能、共通部品、同じデータ、後続業務を見る
* 欠陥報告では、再現手順、期待結果、実績結果を明確に分ける
* テスト進捗報告では、件数だけでなく、欠陥状況、阻害要因、残存リスク、判断事項を伝える

この3回の講義全体を通して、受講者には次の流れを身につけてもらう。

```text
なぜテストするのか
  ↓
何をテストすべきか
  ↓
どう分解するのか
  ↓
どうケース化・シナリオ化するのか
  ↓
どう優先順位を付けるのか
  ↓
どう報告するのか
```
