テストエンジニア育成講座 — 第2回（90分）

仕様を読み、テストを設計する

仕様把握の勘所、テスト観点の洗い出し、そして技法ダイジェスト。「考えて設計する」力を作る。

今日のゴール

  • 仕様書を「疑いながら」読み、書かれていないこと（暗黙の仕様・仕様の穴）に気づける
  • やみくもにケースを書き始めず、観点 → テスト条件 → テストケースの順で考えられる
  • 代表的な技法4つの「使い所」が分かる（練習は課題図書で）
  • 自分のテストケースの「根拠」を他人に説明できる

1. 仕様把握の勘所 — テストは読むことから始まる 20分

テストベースは仕様書だけではない

テストの拠り所（テストベース）＝仕様書、と思いがちですが、実際の現場ではもっと広い情報源を使います。

情報源そこから得られるもの
要件定義書・仕様書・設計書明示された仕様。まずはここから。ただし完全ではない前提で読む
過去の不具合票・障害報告このプロダクトの「壊れやすい場所」（欠陥の偏在）。新しい現場に入ったらまず読むべき資料
問い合わせ・ヘルプデスク記録ユーザーが実際につまずく場所、想定外の使われ方
業務マニュアル・運用手順書システムの外側にある業務の流れ。締め日・月次/年次処理・例外運用
実際の画面・現行システム仕様書に書かれない振る舞い。リプレイス案件では現行が最大のテストベース
人（企画・開発・業務部門）文書化されていない意図・経緯。「聞くこと」も立派な調査活動

仕様書の読み方 — 3つのパスで読む

  1. 1周目: 俯瞰 — 目的から読む。「この機能は誰の・何の業務のためにあるのか」を掴む。細部は読み飛ばしてよい
  2. 2周目: 精読 — 条件・数値・状態を拾いながら読む。「〜の場合」が出てきたらその裏（それ以外の場合）はどうなる？と必ず問う
  3. 3周目: 攻める — テスターの目で読む。「ここを突いたら壊れそう」「この2つの記述は矛盾していないか」を探す。これは静的テストそのもの

「暗黙の仕様」に気づく

仕様書に書かれるのは氷山の一角です。書かれていないが守られるべきことを暗黙の仕様と呼びます。

  • 当たり前すぎて書かれないこと: 保存したデータは消えない、他人の申請は見えない、二重送信でレコードが重複しない
  • 業務の常識: 締め処理後の伝票は修正できない、退職者のアカウントでは申請できない、年度をまたぐ精算の扱い
  • エラー処理の欠落: 正常系しか書かれていない仕様書は非常に多い。「失敗したらどうなるか」は大抵書かれていない

仕様の穴・矛盾の嗅ぎ分け方

兆候問いかけ
「◯◯以上」「◯◯を超える」の混在境界ちょうどはどっち？（5万円「以上」と「超」は1円違う）
用語の揺れ（申請者/起票者/本人）同じ意味？違う意味？代理申請だと誰を指す？
「原則として」「基本的に」例外は何？誰が判断する？
主語がない受け身文誰が／どのタイミングで行う処理？バッチ？画面操作？
更新系の記述だけがある同時に操作したら？途中で失敗したら？取り消せる？

質問力 — 開発者・企画への聞き方

  • Yes/Noで聞かず、自分の理解を仮説として提示する: 「5万円ちょうどは部長承認不要、という理解で合っていますか？」— 相手は差分だけ答えればよく、認識ズレも露見しやすい
  • 質問はまとめて、優先度をつけて持っていく（五月雨に聞かない）
  • 回答は必ず記録し、チームに共有する。口頭で得た仕様は、あなたが文書化した瞬間にチームの資産になる
マインドセット 仕様書を「正解が書いてある答案」ではなく「検証すべき主張」として読む。 仕様の質問がたくさん出るのは、読み込みが深い証拠。遠慮して聞かずに思い込みでテストするのが一番危険。

2. ワーク① 曖昧な仕様から質問リストを作る 15分

ワーク（個人7分 → グループ共有8分）

次の仕様書（抜粋）を読み、開発者・企画に確認すべき質問を最低5つ書き出してください。 「暗黙の仕様」「境界」「例外」の3方向から考えると出しやすいです。

経費精算システム 機能仕様書（抜粋）— §4 経費申請
  1. 社員は経費を申請できる。
  2. 金額は1円以上とする。
  3. 申請金額が5万円を超える場合は、部長の承認が必要となる。それ以外は課長の承認とする。
  4. 申請には領収書を添付すること。
  5. 承認された申請は、翌月の給与とあわせて振り込まれる。
質問リストの例を見る（20個以上出ます）
  • 境界・数値: 5万円「ちょうど」は課長承認でよいか／金額に上限はないのか（1億円でも申請できる？）／小数や負数の入力は弾く仕様か
  • 用語・主体: 「社員」に契約社員・派遣・休職中は含むか／部長が申請者本人の場合は誰が承認するか／代理申請はあるか
  • 添付: 領収書のファイル形式・サイズ上限は／複数枚添付できるか／領収書が出ない経費（電車賃）はどうするか
  • 状態・フロー: 承認前に申請者は修正・取り下げできるか／差し戻しはあるか／承認者が不在（退職・異動）の場合は
  • 時間・業務: 「翌月」の締め日はいつか／月末申請と月初申請の境界は／年度をまたぐ場合の扱いは
  • 暗黙の仕様: 他人の申請は見えないはず／二重申請（同じ領収書を2回）を防ぐ仕組みはあるか

たった5行の仕様からこれだけ出る、ということ自体が今日の学びです。仕様の行数とテストすべきことの量は比例しません。

3. テスト観点 — 何を確かめるかを先に決める 15分

いきなりテストケースを書かない

未経験者が最初にやりがちな失敗は、仕様書を見ながらいきなりExcelにテストケースを書き始めることです。 これをやると思いついた順のケースになり、抜けだらけ・重複だらけになります。順番はこうです:

観点出しのフレーム — 7つの引き出し

ゼロから観点をひねり出すのは無理です。引き出し（フレーム）に沿って機械的に問いかけるのがコツです。

引き出し問いかけ経費申請での例
機能仕様に書かれた振る舞いは正しいか5万円超で部長承認ルートになるか
データ入力の種類・境界・組み合わせは金額の境界値、全角数字、空欄、巨大な添付ファイル
状態対象の状態によって挙動が変わらないか下書き／申請中／差戻し／承認済、それぞれからできる操作
タイミングいつ・どの順で起きると危ないか締め日当日の申請、承認中の申請者による取り下げ、二重クリック
環境動作環境・連携先が変わったらブラウザ差、給与システム連携の失敗時
ユーザー誰が使うと想定と違うか権限違い（一般/課長/部長/経理）、兼務者、退職予定者
組み合わせ複数条件が重なったら差戻し後に金額を5万円超へ修正 → 承認ルートは変わるか

リスクベースで濃淡をつける

観点をたくさん出したら、全部を同じ深さでテストするのではなく、2つの軸で濃淡をつけます。

  • 壊れると痛い所はどこか（業務影響）: お金の計算、締め処理、外部連携、権限まわりは業務システムの急所
  • 壊れていそうな所はどこか（欠陥の偏在）: 新規機能、仕様変更が重なった機能、過去にバグが多発した機能、複雑な条件分岐
マインドセット 「やらないこと」を決めて説明できるのがテスト設計者。薄くする領域は、隠すのではなく宣言する。 「この領域は変更がなくリスクが低いため確認は主要動線のみとします」と言えれば、それは手抜きではなく設計。

4. ワーク② 観点ブレスト 10分

ワーク（グループ10分）

ワーク①の経費申請仕様について、7つの引き出しを使ってテスト観点をチームで20個以上挙げてください。 付箋（またはホワイトボード）に1観点1枚で書き出し、引き出しごとにグルーピングします。

最後に「最も濃くテストすべき観点トップ3」に投票し、理由（業務影響 or 壊れやすさ）を一言添えてください。

5. 技法ダイジェスト — 条件をケースに変換する道具 15分

技法は「賢いテストケースを思いつく魔法」ではなく、観点・条件を漏れなく・ダブりなくケースへ変換する道具です。 今日は代表4つの「使い所」だけ押さえます。手を動かす練習は課題図書（『ソフトウェアテスト技法練習帳』）で。

① 同値分割・境界値分析 — データの観点に

入力を「同じ扱いをされるグループ（同値クラス）」に分け、各グループから代表値を選ぶ。バグは境界に潜むので、境界の両側を必ず突く。

例: 承認ルート（5万円を超えると部長承認） 境界は50,000円。テストすべきは 49,999 / 50,000 / 50,001 の3点。 「以上」なのか「超える」なのかをワーク①で確認したことが、ここで効いてくる。 あわせて下限境界 0 / 1 円も（仕様は「1円以上」）。

② デシジョンテーブル — 条件の組み合わせに

複数の条件で挙動が変わるとき、条件の組み合わせを表にして全パターンの挙動を仕様に問う。埋まらないマスは仕様の穴。

ルール1ルール2ルール3ルール4
金額が5万円を超えるYYNN
申請者が部長職YNYN
承認者は？仕様未定義!部長仕様未定義!課長

表にした瞬間、「部長本人が申請したら誰が承認するのか」という穴が機械的に見つかる。デシジョンテーブルは設計の道具であると同時に、仕様レビューの道具でもあります。

③ 状態遷移テスト — 状態とフローの観点に

状態を持つ対象（申請ステータス、契約状態など）は、状態遷移図を描いて「できるはずの遷移」と「できてはいけない遷移」を確かめる。

  • 特に重要なのが「無効な遷移」の確認: 承認済の申請を申請者が編集できてしまったら、承認の意味がなくなる（業務統制の崩壊）

④ 探索的テスト — スクリプトの外側を補う

事前に書いたケース（スクリプトテスト）だけでは、書いた人の想像の範囲しか確かめられません。 「◯◯を60分間、△△の観点で探索する」というお題（チャーター）を決めて自由に触り、学びながらテストするのが探索的テスト。 スクリプトの対極ではなく補完です。新しい機能を受け取ったら、まず30分探索してからケースを書くと設計の質が上がります。

良いテストケースの条件

  • 目的（確かめたい条件）が1つに絞れている
  • 期待結果が具体的（「正しく表示される」はNG。「1,111円と表示される」まで書く）
  • 前提条件・データが書かれていて、他人が・半年後の自分が同じように実行できる
  • どの観点・仕様に基づくかを辿れる（トレーサビリティ）— 仕様変更のとき、直すべきケースがすぐ分かる

6. ワーク③ 境界値とデシジョンテーブルでケース化 10分

ワーク（ペア10分）

ワーク②で出した観点のうち「金額と承認ルート」について、次の2つを作ってください。

  1. 金額の境界値一覧（テストすべき金額のリストと、それぞれの期待結果）
  2. 「金額 × 申請者の役職」のデシジョンテーブル。仕様が未定義のマスには「要確認」と書く

完成したらペアを交換して相互レビュー: 「期待結果は具体的か」「境界の両側があるか」を確認し合う。

まとめと宿題 5分

今日の持ち帰り

  • テストベースは仕様書だけではない。過去の不具合票と「人」は特に重要な情報源
  • 仕様書は3周読む（俯瞰→精読→攻める）。「〜の場合」の裏を必ず問う
  • いきなりケースを書かない。観点 → 条件 → ケース。観点は7つの引き出しで機械的に出す
  • 濃淡はリスクで決め、「やらないこと」は宣言する
  • 技法は変換の道具。境界値・デシジョンテーブル・状態遷移は仕様の穴の発見器でもある

宿題（30分程度）

  • 『ソフトウェアテスト技法練習帳』の同値分割・境界値の章を1章分解く
  • 担当プロダクトの1機能について、7つの引き出しで観点を10個出してみる（次回冒頭で数人に共有してもらいます）
