テストエンジニア育成講座 — 第3回（90分）

テストを管理し、品質を語る

テスト計画と見積り、PB曲線の読み方、バグトリアージ、そしてテストの終わり方。「回す」力を作る。

今日のゴール

  • テスト計画に何を決めて書くべきかが分かる（特に開始基準・終了基準・やらないこと）
  • 消化曲線とPB曲線を読み、グラフの裏にある現場の状況を想像してから判断できる
  • バグトリアージで、テスターとして意思を持った材料を出せる
  • 「テストの終わり」を残存リスクの言葉で語れる

1. テスト計画と見積り — 始める前に勝負は半分決まる 20分

テスト計画に書くこと

テスト計画書は儀式の文書ではなく、関係者と交わす「合意」のかたまりです。最低限これを決めます。

項目決めること・ポイント
スコープテストする機能・レベル・タイプ。そして「やらないこと」を明記する（第2回参照）。やらないことが書かれていない計画は、後で「やってくれてると思った」を生む
アプローチどの領域をどの濃さで（リスクベースの濃淡）。新規機能は設計ベースで厚く、既存部はリグレッション中心、など
開始基準（エントリ）テストを受け入れる条件: 単体テスト完了、環境・テストデータが揃っている、主要動線が最低限動く（スモーク通過）など
終了基準（イグジット）「いつ終わってよいか」: ケース消化率、未解決バグの重要度別件数、カバレッジなど。始める前に決めておくのが肝
スケジュール・体制誰が・いつ・何を。バグ修正待ちと再テストの時間を織り込む
リスクと前提「環境提供が遅れたら開始も遅れる」等、崩れたら計画が変わる前提を書いておく — これが後の交渉材料になる

開始基準を軽視すると地獄が始まる

経験の浅いチームが最も痛い目に遭うのがここです。単体テストが不十分なままシステムテストを始めると、 初日から基本動作のバグで手が止まり、本来の観点のテストに一切進めないという消耗戦になります。

マインドセット 基準を満たさない成果物は受け入れを保留する勇気を持つ。ただし喧嘩ではなく交渉で。 「この状態で受けると全体が遅れます。スモークが通る状態で受ける方が結局早いです」と、相手の利益で語る。

見積りの現実 — 実行時間だけ数えると必ず破綻する

  • テスト見積り ＝ 実行時間だけではない。分析・設計・データ準備・環境確認・バグ票起票・再テスト・リグレッションを含める
  • 経験則: バグ対応（起票・確認・再テスト）で実行工数と同等以上かかることも珍しくない。バグが多い前提の機能なら、なおさら
  • 業務システム特有の重さ: テストデータ作り（マスタ・権限・月次状態の組み合わせ）と環境・連携先の調整は、見積りから最も抜けやすく、最も遅延を生む
  • 締め日・月次処理があるシステムは「その日付にならないと確認できない」テストがある。カレンダーを最初に確認する
マインドセット 計画は「約束」ではなく「その時点の情報で合意した仮説」。状況が変わったら隠さず更新して再合意する。 黙って頑張って最後に「間に合いません」が最悪のパターン。

2. 進捗と品質を読む — 消化曲線とPB曲線 20分

2つのグラフで現在地を見る

  • 消化曲線: テストケースの消化数（予定と実績）を日ごとに折れ線で。進捗を見る
  • PB曲線（バグ曲線／信頼度成長曲線）: 累積バグ発見数を折れ線で。品質の安定度を見る
  • この2つは必ずセットで読む。バグ曲線だけ見ても、テストが進んでいないのか品質が良いのか区別できない

PB曲線の基本の見方

テスト序盤はバグが多く見つかり、順調に進めば発見ペースが落ちて曲線が水平に近づく（「曲線が寝る」＝収束のサイン）。 理想は緩やかなS字です。ただし——

グラフは嘘をつく — 4つのパターン

形ありがちな解釈本当に確かめるべきこと
A 順調に収束。リリース可能 消化曲線も計画通りか。難しいケースを後回しにして寝ているだけではないか。終盤の消化ケースの中身を見る
B 品質が悪い。リリース不可 本当に品質問題か、それともテストが優秀でバグを掘り当て続けているのか。バグの重要度の内訳と発生機能の偏りを見る。特定機能に集中しているなら、その機能の作り直し判断も視野に
C 早く収束した。品質が良い 一番危険な形。テストが止まっていないか（環境障害・ブロックバグ・要員離脱）、簡単なケースだけ消化していないか、バグ起票をサボっていないか。消化曲線とセットで見れば一発で分かる
D よく分からない動き ケース消化をまとめてやっていないか（週末にまとめて実行）、バグ報告が遅延・まとめ起票されていないか。運用の問題であってプロダクト品質の問題ではないかも
現場の鉄則 メトリクスは会話の入口であって、結論ではない。グラフを見て言ってよいのは「リリースできる/できない」ではなく 「この形になっている理由を確認しよう」。数字の裏を現場に確かめてから判断する。 逆に、自分が報告する側になったら「グラフ＋その裏で起きていること」をセットで語る。
業務システムの現場から 消化率95%・バグ曲線も寝ていて「順調」に見えたプロジェクト。残り5%が「月次締めバッチ」のケースで、 実行できる日が月末しかなく、最後の最後で重大バグが噴出——という失敗は本当によくある。 残ケースの「数」ではなく「中身」を見る癖をつける。

3. ワーク① このプロジェクト、リリースしてよい？ 20分

ワーク（グループ15分 → 発表5分）

グループごとに、上のA〜Dいずれかのグラフ＋「状況カード」（講師が配布: 消化率、残バグの重要度内訳、残ケースの中身、チーム状況）を受け取ります。

  1. リリース判定会議に出すつもりで、「現状の品質状況」「リリース可否の推奨」「可否を判断するために追加で確認すべきこと」を3分で説明できる形にまとめる
  2. 各グループ発表。他グループは「その判断、数字の裏は取れてる？」の視点でツッコミを入れる
講師用: 状況カードの例
  • Aグラフ用: 消化率98%。ただし未消化の2%は権限×月次締めの組み合わせケース。残バグは重要度低が3件。→「順調に見えるが残りが急所」に気づけるか
  • Bグラフ用: バグの7割が新規機能「電子帳簿連携」に集中。他機能は収束傾向。→「全体NG」ではなく「特定機能の品質問題」と切り分けられるか
  • Cグラフ用: 10日前から検証環境が不安定でテストが半分止まっている。→ グラフが寝た理由は品質ではないと見抜けるか
  • Dグラフ用: テスターがバグ票を週1でまとめて起票していた。→ プロセス改善の話であり、品質判断には起票遅延を補正した見方が必要と気づけるか

4. バグトリアージ — 直す順番を決める会議の回し方 10分

トリアージとは

見つかったバグ全部を直す時間はありません（全数テスト不可能の親戚です）。 重要度・頻度・回避策の有無から優先度を決め、「今直す／次のリリースで直す／直さないと決める」を関係者で合意するのがトリアージです。

判断軸問いかけ
業務影響（重要度）壊れると業務が止まるか。お金・法令・締め処理に関わるか。影響するユーザー数は
発生頻度・条件誰でも毎回踏むのか、特定条件のみか。月次でしか発生しなくても、締め日に全員が踏むなら高頻度と同じ
回避策の有無運用でしのげるか（手作業で代替できるか）。回避策があるなら優先度を下げられる。ただし回避策の運用コストも見積もる
修正リスク直すことで他を壊さないか。リリース直前の修正は、それ自体がリスク

テスターの役割 — 意思を持って材料を出す

  • 優先度の最終決定はプロダクト側の仕事。しかし「決められる材料」を揃えるのはテスターの仕事: 再現条件、影響範囲、頻度、回避策の有無まで調べて出す
  • 単なる報告係にならない。「私はこれをP1相当と考えます。理由は締め日に経理全員が踏むからです」と推奨＋根拠まで言う。採用されなくてよい。考えを持って出すことに意味がある
  • 「直さない」と決まったバグは、既知の問題として残存リスクに記録する。ここでうやむやにすると、リリース後に「聞いてない」が起きる
マインドセット トリアージは開発 vs テストの勝負の場ではなく、限られた時間をどこに使うかをチームで決める場。 「全部直してください」は思考停止。優先順位を語れるテスターがチームの信頼を得る。

5. テストの終わり方 — 残存リスクを語る 10分

テストは「バグが0になったら終わり」ではない

バグは0にならないし、0に見えてもいないことは証明できません（第1回・7原則）。 テストの終わりは計画時に合意した終了基準を満たしたかどうかで判断し、 満たせない場合は何が残っているかを明らかにして、リリース判断者に委ねるのが正しい終わり方です。

テストサマリーレポート — 最後の成果物

書くことポイント
実施したこと／しなかったこと計画とスコープに対する実績。やらなかったことを隠さない
結果サマリー消化数、バグ数と重要度内訳、収束状況（グラフ＋裏の状況説明）
残存リスク未解決バグ（回避策つき）、テストできなかった領域とその理由、薄くした領域
推奨「リリース可否の判断材料として、以上を報告します。テストチームとしては〜を推奨します」

これが第1回の冒頭に言った「テストの成果物は品質に関する判断材料」の最終形です。 良いサマリーレポートが書けること＝テストを一人で回せること、と言ってもいいくらいです。

マインドセット（総集編）
  • 悪い報せほど早く・正確に。盛らない、隠さない、憶測で断言しない
  • 「テスト済み＝バグゼロ」とは決して言わない誠実さが、あなたの報告の価値を作る
  • 品質はテストチームだけのものではない。開発・企画・業務部門と同じ側に立って品質を作る

まとめ・これからの学び方 5分

3回の講座の全体像

  • 第1回: テストは品質情報で意思決定を支える仕事。限界を知り、バグ票という武器を持った
  • 第2回: 仕様を疑って読み、観点→条件→ケースの順で、根拠を説明できる設計をする
  • 第3回: 計画で合意し、グラフの裏を読み、トリアージで意思を出し、残存リスクを語って終える

この3つのループを、小さな案件でよいので一人で最初から最後まで回せるようになるのが次のステップです。

この先のキャリア — テストの先に広がる道

「テスト設計・管理を一人で回せる」はゴールではなく、キャリアの分岐点です。 そこから先には複数の専門性への道が開けます。どの道に進んでも、この3回で扱った「考え方」がそのまま土台になります。

  • テストスペシャリスト / テストアーキテクト: テスト分析・設計そのものを極める道。大規模なテスト設計を構造化し、チームの設計標準を作る。第2回の内容を深めていく方向（ISTQB Advanced Level: Test Analyst が指針になる）
  • QAエンジニア（品質保証）: テスト工程の外に出て、品質データの分析、開発プロセスの改善、上流での欠陥予防（シフトレフト）に関わる道。「テストで品質を測る」から「プロセスで品質を作り込む」へ視点が一段上がる。バグの傾向分析から「そもそもなぜこのバグが混入したか」を追うのが入口
  • SET / テスト自動化エンジニア: コードを書いてテストを支える道。リグレッションテストの自動化、CI/CDへの組み込み、開発者へのテスタビリティ（テストしやすさ）の提案。開発スキル×テストスキルの掛け算で希少価値が高い
  • テストマネージャー / QAマネージャー: 複数案件・複数チームの計画、体制づくり、品質戦略の立案。第3回で扱った「回す力」を組織スケールに広げる道（ISTQB Advanced Level: Test Manager が指針になる）

いま選ぶ必要はありません。まずは1年、テスト設計と管理のループを回しきって、自分の「得意」と「好き」がどこにあるかを見つけてください。

学びを続けるために

  • 書籍: 『ソフトウェアテスト技法練習帳』（技法の筋トレ）、『ソフトウェアテスト講義ノオト』（体系の復習）、『知識ゼロから学ぶソフトウェアテスト』（読み物として）
  • 資格: この講座はISTQB Foundation Level（CTFL 2023 V4.0）の体系に沿っています。腕試しにJSTQB認定テスト技術者資格（FL）の受験もおすすめです。シラバスはJSTQB公式サイトで無料公開されています
  • コミュニティ: JaSST（ソフトウェアテストシンポジウム）など。現場の外の空気を吸うと視野が広がります
